# ENE 안드로이드 LAN 동반 앱 V1 설계

작성일: 2026-09-07

상태: 승인된 V1 범위에 재검토 보완과 향후 확장 원칙을 반영한 통합 명세. 구현 완료를 뜻하지 않는다.

2026-09-08 전송 보안 변경: 사용자가 HTTPS/WSS 전환 방향을 선택했다. 아래 평문 제외 규칙과 [TLS 전환 부속 명세](2026-09-08-ene-companion-tls-design.md)를 적용한다. 부속 명세의 인증서 수명·복구 세부 규칙은 문서 검토 대상이며, 현재 코드의 암호화 완료를 뜻하지 않는다.

이 문서는 [이전 모바일 원격 APK 설계](2026-05-23-ene-mobile-remote-apk-design.md)를 대체한다. 이전 문서의 음성·Live2D·첨부·외부 접속 범위를 현재 V1 요구사항으로 합치지 않는다.

2026-09-16 후속 결정: 사용자는 설치·실기기 시험을 보류하고 음성·캐릭터·쓰다듬기·공통 설정 확장을 진행하기로 했다. 아래 텍스트 V1 범위는 기준으로 보존하며, 추가 범위와 자동 음성 출력은 [캐릭터·음성 확장 설계](2026-09-16-ene-companion-media-design.md)를 따른다. 실제 ENE 대화 통합이 먼저 필요하며, 단말 인수는 미검증 상태다.

## 1. 목표와 범위

실행 중인 PC ENE에 안드로이드 앱을 연결하여, 신뢰하는 개인 LAN에서 같은 현재 대화를 읽고 텍스트를 보낸다. PC와 휴대폰은 서로 통신할 수 있는 동일 네트워크에 있어야 한다. PC의 유선 연결도 허용한다. 같은 Wi-Fi 이름만으로 기기 간 통신 가능 여부가 보장되지는 않는다.

- PC가 AI 호출, 기억, 설정, 현재 대화의 권위를 가진다. 모바일에는 AI 제공자 키를 전달하지 않는다.
- 처음 연결하거나 다시 연결하면 현재 대화 전체를 받는다. 과거에 종료한 다른 대화의 탐색은 제외한다.
- 모바일 대화·입력 초안·전송 대기 정보는 메모리에만 유지한다. 프로세스 종료 후에는 PC에서 다시 받는다.
- 안드로이드 한 대만 등록한다. 새 기기의 승인이 완료되면 이전 등록을 교체한다.
- PC에서 생성한 2분 유효 일회용 QR을 앱이 스캔하고, PC에서 승인해야 등록된다.
- Android는 Kotlin·Jetpack Compose 네이티브 앱이다. QR 연결, 승인 대기, 텍스트 대화, 연결 상태, 주소 변경·등록 해제를 제공한다.
- 음성 입력·출력, 캐릭터, 첨부 전송, 모바일 편집·리롤·초기화 버튼, 과거 대화 검색, 오프라인 전송, 백그라운드 알림은 제외한다.
- 최초 정보 조회부터 페어링·대화까지 HTTPS/WSS로 암호화하고 QR로 등록한 PC 신원을 검증한다. 평문 연결과 평문 자동 전환은 제공하지 않는다.
- Tailscale 통합·설정·검증, 외부 접속, 중계 서버, 포트포워딩과 자체 메시지 암호화 프로토콜은 제외한다. 표준 TLS 전송 보안은 V1에 포함한다.

복잡도는 중간이다. UI보다 현재 대화 전체의 유지, 중복 방지, PC 작업 상태와의 결합이 핵심이다.

네이티브 선택은 V1의 연결·대화 UI를 단순하게 구성하기 위한 결정이다. 네이티브라는 이유만으로 안정성을 보장하거나, 이전 실패 원인을 WebView 자체로 단정하지 않는다. 안정성은 수락·동기화·연결 수명 규칙과 실기기 검증으로 확인한다.

## 2. 저장소와 구현 경계

두 폴더는 같은 상위 폴더 아래의 독립 저장소로 관리한다.

| 위치 | 책임 |
| --- | --- |
| `ENE/` | Python 통신 서버, 페어링 승인 UI, PC 대화 연동, 통신 규격 원본 |
| `ENE_APP/` | Kotlin 앱, Android 권한·인증정보 보관·연결·화면, Android 테스트 |

`ENE_APP`을 `ENE` 안에 넣거나 Git 서브모듈로 만들지 않는다. 각각의 커밋과 원격 저장소를 사용한다. GitHub 원격 생성·공개·업로드는 별도 게시 단계다. APK는 소스 관리 대상이 아닌 빌드 산출물이며, 배포 시 서명과 산출물 검사를 거친다.

통신 계약은 `protocol_version = 1`인 JSON으로 정의한다. 구현 계획 단계에서 `ENE`의 규격과 중립적인 계약 테스트 데이터를 작성하고 `ENE_APP`에 동일 버전을 복사한다. Python 소스를 앱에 복사하거나 세 번째 공용 저장소를 만들지 않는다.

2026-09-07 확인 시 `ENE_APP`은 빈 폴더이며 Git 저장소가 아니다. 현재 작업 환경의 쓰기 허용 범위 밖이므로 실제 앱 파일 생성 시 해당 경로 쓰기 권한을 확보해야 한다. 이 명세 작성에는 해당 경로 변경이 필요 없다.

## 3. 현재 코드에서 확인한 제약과 보완

확인 기준은 ENE 커밋 `e84103cf`다. 이후 구현 전 관련 변경만 재확인한다.

- `src/core/bridge.py`의 `_append_conversation()`은 `conversation_buffer`에 추가한다.
- `src/core/bridge_mixins/memory_summary.py`는 요약한 항목을 버퍼에서 제거하거나 버퍼를 비운다. 따라서 이 버퍼는 전체 화면 대화 기록이 아니다.
- `assets/web/runtime_chat_flow.js`는 PC 입력을 수락 확인 전에 화면에 추가하고 입력창을 비운다. 현재대로면 동시 전송에서 거절된 PC 입력이 사라질 수 있다.
- `src/core/bridge_mixins/chat_flow.py`의 `send_to_ai()`는 명시적 접수 결과를 반환하지 않는다. 함수 호출 자체를 메시지 접수 성공으로 간주하면 안 된다.
- `assets/web/runtime_message_rendering.js`의 PC 편집 호출에는 대상 ID가 없고, `bridge_mixins/chat_flow.py`의 편집·리롤은 최신 요청 정보를 사용한다. 편집창을 열어 둔 동안 모바일 대화가 추가되면 다른 메시지를 수정할 수 있으므로, 실제 수락 시 대상과 개정을 검증해야 한다.
- 답변은 내부 버퍼에 들어온 뒤 PC의 TTS 준비에 따라 나중에 표시될 수 있다. 대화 공개 시점과 내부 생성 완료를 구분해야 한다.
- `src/core/bridge_state.py`와 `bridge_mixins/life_records.py`에 단일 작업 상태와 작업 식별자가 이미 있다. 모바일 전용의 별도 AI 잠금을 겹쳐 만들지 않는다.

이를 반영해 기존 아키텍처의 단일 PC 권위는 유지하되, 화면 표시용 `CurrentConversationTranscript`를 Qt 메인 스레드에 둔다. 이 기록은 앱 실행 초기부터 유지하여 모바일을 나중에 켜도 이전 현재 대화를 제공한다. 요약 버퍼를 그대로 전송한다는 초기 구상은 이 설계로 정정한다.

## 4. 구성 요소와 스레드 소유권

| 구성 요소 | 책임과 소유권 |
| --- | --- |
| `CompanionGateway` | 기존 의존성인 aiohttp 사용. 전용 이벤트 루프에서 HTTPS/WSS, 제한 시간, 연결 큐 관리 |
| PC TLS 신원 보관·Android 전용 신뢰 설정 | PC 인증 키·인증서 수명과 QR 기반 신뢰 검증. IP 주소와 인증 신원을 분리하고 개인키는 PC 밖으로 전송하지 않음 |
| `PairingService` | QR 수명, 승인 대기, 등록 세대, 인증 검증. 서버 루프에서 직렬 처리 |
| `CompanionBridgeAdapter` | 등록·게이트웨이 세대가 포함된 요청을 Qt에 전달하고 결과를 반환. UI·대화·AI 객체를 네트워크 스레드에서 직접 호출하지 않음 |
| `CurrentConversationTranscript` | 현재 표시 대화와 개정 번호를 Qt 메인 스레드에서 관리. 읽기용 스냅샷과 변경 이벤트 제공 |
| 기존 `WebBridge` 및 작업 상태 | PC·모바일의 메시지 수락, AI 실행, 기억과 부수효과의 단일 처리 경로. 요청 처리 원장은 현재 대화 상태에 귀속하여 Qt 메인 스레드가 소유 |
| Android `ConnectionRepository` | QR, 인증정보 접근, 주소 후보, 연결 상태, 재동기화. 연결 시도는 동시에 하나 |
| Android `ChatViewModel` | 메모리 내 대화·초안·전송 상태를 Compose에 전달. 화면 회전에 연결이나 AI 요청을 다시 생성하지 않음 |

Qt에는 큐잉된 신호로 전달하고 서버 루프에는 스레드 안전 예약 방식으로 돌려준다. 변경 가능한 리스트·딕셔너리를 두 스레드가 공동 수정하지 않는다. GUI 스레드에서 네트워크 응답을 기다리지 않는다.

네트워크 연결 객체가 요청 처리 원장의 원본을 소유하지 않는다. 게이트웨이만 껐다 켜도 표시 기록·요청 원장·진행 중 작업은 PC의 현재 대화와 함께 유지한다. 네트워크 객체에는 불변 결과 사본만 전달한다.

## 5. 서버 시작과 주소

- 최초 기본값은 모바일 연결 꺼짐이다. 사용자가 PC에서 모바일 연결을 활성화하면 그 선택을 저장하고 서버를 시작한다.
- 활성화 상태에서는 ENE 재실행 시 서버도 시작한다. 연결 끄기는 모든 소켓과 승인 대기를 닫고 자동 시작을 끈다. 등록 해제와는 구분한다.
- 기본 바인딩은 IPv4 `0.0.0.0:8765`이며 PC 설정에서 포트를 변경할 수 있다. 포트 충돌 시 조용히 다른 포트로 이동하지 않고 조치 가능한 오류를 표시한다.
- TLS 신원·비밀키 보관·인증서 유효성 검증과 실제 TLS 포트 리슨이 모두 성공한 이후에만 연결 가능 상태와 QR을 표시한다. 실패하면 평문 리스너를 대신 시작하지 않는다.
- QR에는 활성 어댑터의 접속 가능한 IPv4 주소 후보를 중복 없이 최대 8개 담는다. `0.0.0.0`, 루프백, 연결이 끊긴 어댑터는 제외한다.
- 각 주소 시도에는 제한 시간을 둔다. 성공한 주소를 우선 사용하되 대체 주소를 잃어버리지 않는다. QR 암호만 다시 해석하여 주소 목록을 덮어쓰지 않는다.
- 앱에서 호스트와 포트를 직접 수정할 수 있다. SSID 일치나 `192.168.*` 여부를 연결 조건으로 하드코딩하지 않는다. 네트워크 자동 검색은 V1에서 제외한다.
- Windows 방화벽 설정 안내는 개인 네트워크·해당 실행 파일·해당 포트·로컬 서브넷 범위로 한정한다. 방화벽을 자동 해제하거나 공용 프로필에 포트를 열지 않는다.
- 개인 LAN 전용은 사용·검증 범위다. `0.0.0.0` 바인딩 자체가 LAN만 허용하는 접근 제어는 아니며 실제 노출 범위는 OS 방화벽에 의존한다.

## 6. 페어링, 인증, 기기 교체

### 6.1 최초 등록

1. PC가 암호학적으로 안전한 난수 32바이트로 일회용 QR 암호를 만든다. 버전·PC 식별자·주소 후보·페어링 식별자·만료 정보와 함께 TLS 전송 표시와 해당 PC 전용 공개 CA 인증서를 표시한다. 개인키는 포함하지 않는다.
2. 서버는 단조 시간 기준 120초를 적용한다. 새 QR 발급은 이전 QR과 그 승인 대기를 취소한다.
3. 앱은 QR 구조·인증서를 검증하고 그 PC만 신뢰하는 TLS 연결로 정보 조회와 페어링 전용 WSS를 연다. 실제 페어링 연결에서도 인증서 체인과 고정 서버 이름을 검증한 뒤에만 QR 암호를 최초 메시지 본문으로 보낸다. URL 쿼리에 넣지 않는다.
4. 첫 유효 요청에 QR을 묶는다. 동시에 들어온 다른 요청은 거절한다. 이 연결에는 등록 승인 상태 외의 대화 정보를 보내지 않는다.
5. PC에서 기기 표시명과 기존 기기 교체 여부를 보여준다. 승인·거절은 로컬 PC UI만 실행할 수 있다. 원격 승인 API를 만들지 않는다.
6. QR 만료 전에 승인한 경우 새 무작위 기기 토큰을 생성하고 검증용 해시·기기 식별자·등록 세대를 원자적으로 저장한다. 저장 실패 시 파일이 이전 상태 그대로임을 확인한 경우에만 기존 등록을 유지하고 승인 실패를 알린다. 교체 후 내구 확인 오류 등 저장 결과가 불명확하면 모바일 인증·새 접수를 차단한 채 서버 재시작과 등록 상태 재확인을 요구한다. 이 경우 이전 등록이 유지되었다고 보장하지 않는다.
7. 등록 교체가 성공하면 이전 세대의 연결과 대기 요청을 무효화하고 새 토큰을 해당 페어링 소켓에 한 번 전달한다. 토큰 전달 중 끊기면 QR부터 다시 등록한다. PC에는 토큰 원문을 영구 저장하지 않는다.
8. QR과 승인 대기는 소비된다. 거절·만료·소켓 종료도 해당 시도를 종료하며 새 QR이 필요하다.

### 6.2 재접속과 폐기

- 일반 WSS 연결은 실제 TLS 연결의 PC 신원 검증 이후 인증 헤더로 기기 토큰을 전달한다. 서버는 충분히 긴 무작위 토큰의 SHA-256 해시를 상수 시간 비교로 검증한다.
- 토큰은 요청의 임의 기기 이름이 아니라 저장된 등록 세대와 연결된다. 기기 교체·등록 해제 시 열린 소켓뿐 아니라 Qt에 대기 중인 구세대 요청도 접수 전에 거절한다.
- 교체 시점과 요청 수락 시점의 순서는 Qt와 서버 간 확인 절차로 정한다. 폐기 완료를 PC에 표시한 이후 구세대 요청을 새로 수락해서는 안 된다.
- 폐기 전에 이미 수락한 AI 작업은 계속 완료할 수 있다. 결과는 현재 권한이 있는 PC와 앱에만 전송한다.
- 동일 등록 기기의 새 일반 연결은 기존 소켓을 교체한다. 늦게 도착한 이전 연결 콜백은 현재 연결 상태를 바꾸지 않는다.
- PC 등록 해제는 토큰 검증 기록을 폐기한다. 앱은 해당 서버의 명확한 인증 실패 시 토큰과 대화를 지우고 페어링 화면으로 돌아간다.
- 주소 오류·연결 시간 초과·TLS 검증 실패만으로 기존 토큰과 신뢰 정보를 삭제하거나 교체하지 않는다. 다른 인증서나 PC 식별자를 만난 후보에는 토큰을 보내지 않는다. 올바른 후보가 없으면 주소·시계·PC 인증 정보 확인을 안내한다. 새 신뢰 정보 등록은 새 QR과 PC 승인으로만 수행한다. 단순 `server_id` 비교는 TLS 검증을 대체하지 않는다.

### 6.3 보관과 전송 보안

기기 토큰은 Android Keystore에 임의 문자열로 직접 넣지 않는다. Keystore에 생성한 비추출 암호화 키로 토큰과 그 토큰에 대응하는 PC 신뢰 정보를 함께 암호화하고 앱 전용 저장소에 원자적으로 보관한다. 주소와 PC 식별자는 비밀이 아닌 연결 설정으로 별도 보관한다. 토큰·신뢰 정보·연결 설정의 클라우드 백업 및 기기 이전 복원을 제외하고, 대화·초안은 파일·로그·저장 상태 번들에 쓰지 않는다. 키를 사용할 수 없으면 다시 등록한다. [Android Keystore 문서](https://developer.android.com/privacy-and-security/keystore)

V1은 HTTPS/WSS의 TLS 암호화와 PC 신원 검증으로 네트워크상의 대화·QR 암호·토큰 도청 및 서버 사칭 위험을 줄인다. 인증서는 APK에 공통으로 넣지 않고 PC 설치마다 생성하여 QR로 등록한다. 감염된 PC·휴대폰, 유출된 PC 개인키, 실제 QR을 본 공격자, 서비스 거부나 접속 시각·통신량 노출까지 해결한다고 주장하지 않는다. QR은 신뢰하는 PC 화면에서 직접 스캔하고 로컬 승인 규칙을 유지한다. 공용·학교·회사·게스트 네트워크와 외부 공개는 여전히 지원하지 않는다.

Android 네트워크 보안 설정에서 평문 HTTP/WS를 명시적으로 차단한다. 인증서 무검증, 서버 이름 검증 해제, 시스템 전체 CA 설치, 신뢰 목록 자동 확대를 하지 않는다. QR의 PC 전용 CA만 신뢰하는 표준 인증서 체인 검증과 기본 서버 이름 검증을 사용하며 리다이렉트·시스템 프록시·자동 인증 공급자를 사용하지 않는다. 인증서 갱신·신뢰 교체·IP 변경 처리는 부속 명세를 따른다. [Android 네트워크 보안 설정](https://developer.android.com/privacy-and-security/security-config), [TLS 인증서 검증 안내](https://developer.android.com/privacy-and-security/security-ssl)

## 7. 현재 대화의 정확한 의미

- 현재 대화는 PC 앱의 현재 세션에서 표시한 사용자 메시지와 ENE 답변의 전체 논리적 텍스트다. 말풍선 분할·타이핑 효과는 메시지 수를 늘리지 않는다.
- 표시용 기록에는 안정적인 메시지 ID·역할·텍스트·표시 시각을 둔다. 모바일 발신에는 요청 ID를 함께 연결한다. 프롬프트, 내부 생각, 분석 JSON, 기억 원문과 첨부 원본·로컬 경로를 내보내지 않는다.
- PC에서 첨부와 함께 쓴 사용자 텍스트 및 그에 대한 답변은 보여준다. 첨부 자체는 중립적인 미지원 표시만 제공한다. V1에서 모바일 업로드나 파일 열기를 추가하지 않는다.
- 기록은 `WebBridge`의 수락·표시·교체·초기화 경계에서 갱신한다. 화면 DOM을 긁거나 AI 컨텍스트에서 과거 메시지를 복원하지 않는다.
- 사용자 메시지는 PC에서 수락한 시점에 확정한다. 답변은 PC의 표시 이벤트와 같은 논리적 시점에 공개한다. TTS 대기와 재시도 때문에 같은 답변을 두 번 추가하지 않는다.
- 요약에 따른 AI 버퍼 정리는 표시용 기록을 지우지 않는다. 명시적 대화 초기화는 새 대화 식별자를 만들고 화면 기록을 초기화한다.
- PC 편집·리롤은 해당 메시지 ID를 기준으로 기록을 교체하고 앱에 전체 스냅샷을 보낸다. 실패·취소 시 최종 PC 화면과 기록이 일치하도록 기존 결과 복원 또는 오류 표시 상태를 함께 처리한다.
- PC 편집 시작 및 리롤 버튼이 가리키는 화면 상태에 `server_epoch`, `conversation_id`, `target_message_id`, `expected_revision`을 연결하고 명령에 포함한다. 편집 대상은 사용자 메시지, 리롤 대상은 교체할 답변이다. Qt의 실제 수락 시 현재 대화 개정, 허용되는 최신 대상 및 그에 대응하는 원본 요청 정보를 함께 검증한다. 기존의 최신 요청으로 대상을 임의 대체하지 않는다.
- 대화가 바뀌면 `stale_session`, 같은 대화에서 대상·개정이 바뀌면 `stale_target`으로 거절한다. 거절 시 AI 호출·기억 변경·기록 교체를 하지 않고 화면을 재동기화하며 편집 초안을 보존한다. PC 화면도 수락 전에 원래 말풍선을 확정 교체하지 않는다. 작업 중 버튼 비활성화만으로 이 검증을 대신하지 않는다.
- PC 재시작은 새 실행 식별자와 현재 대화를 만든다. V1은 종료된 대화의 새 영구 저장·복원을 추가하지 않는다. 이미 PC가 사용하는 기억 저장 동작은 기존 기능의 책임이다.

## 8. 통신과 동기화 규칙

### 8.1 계약

| 항목 | 규칙 |
| --- | --- |
| 버전 | `protocol_version = 1`의 기본 텍스트 계약 유지. 지원하는 계약이 없으면 대화 수신 전에 명확히 거절 |
| 실행 식별자 | PC 프로세스 시작마다 새로운 `server_epoch` |
| 대화 식별자 | 현재 대화를 구별하는 `conversation_id`, 초기화 시 변경 |
| 대화 개정 | `conversation_revision`은 같은 대화의 표시 기록 추가·교체마다 증가. PC 편집·리롤의 `expected_revision`과 비교 |
| 스냅샷 식별자 | 캡처마다 새로운 `snapshot_id`, 시작·부분·종료에 동일 값 포함 |
| 이벤트 순서 | 같은 대화 안에서 `event_seq`가 증가, 스냅샷 기준 번호 포함 |
| 메시지 ID | 본문의 동일 여부와 무관한 안정적 ID, 편집 시 유지 |
| 요청 ID | 모바일이 생성한 UUID, 재전송에서 유지 |
| 최소 메시지 종류 | 인증 결과, 스냅샷 시작·부분·종료, 대화 추가·교체 알림, 처리 상태, 요청 결과, 오류, 연결 생존 확인 요청·응답 |

외부에 노출하는 명령은 페어링·인증·현재 대화 읽기·일반 텍스트 전송으로 제한한다. 임의 `WebBridge` 메서드 호출이나 `/note`, `/diary`, `/obs` 같은 파일 작업 명령 실행을 모바일 API로 노출하지 않는다. 이런 명령은 명시적인 미지원 오류를 반환한다. 일반 채팅의 기존 AI·기억 처리 경로는 재사용한다.

### 8.2 전체 스냅샷과 실시간 이벤트

1. 인증 후 Qt 스레드에서 현재 기록, 처리 상태, 실행·대화 식별자, 대화 개정과 기준 이벤트 번호를 함께 캡처한다. 이벤트 구독과 캡처의 경계에서 누락 구간이 없어야 한다.
2. 캡처 이후 이벤트는 해당 연결의 큐에 순서대로 쌓는다. 네트워크 스레드가 현재 대화 객체를 직접 읽지 않는다.
3. 스냅샷은 크기가 제한된 순번 있는 부분 메시지로 전송한다. 큰 단일 메시지도 분할 전송할 수 있어야 한다. 전체 내용을 임의 개수로 잘라 성공 처리하지 않는다.
4. 앱은 임시 메모리에서 순번·완료 표시·실행·대화·스냅샷 식별자를 검증한 후 한 번에 화면을 교체한다. 이전 `snapshot_id`의 늦은 부분 메시지는 폐기한다. 부분 수신 내용을 완성된 대화처럼 표시하지 않는다.
5. 스냅샷의 기준 번호보다 큰 이벤트만 순서대로 적용한다. 중복 번호는 무시하고 번호가 빠지면 전체 동기화를 다시 수행한다.
6. 동기화 중 초기화·편집·리롤이 발생하면 이전 부분 스냅샷을 폐기하고 새 스냅샷으로 전환한다. 세션별 번호만 비교해 새 대화와 이전 대화를 혼합하지 않는다.
7. 과도한 데이터 크기·수신 지연으로 자원 한도를 넘으면 명확한 동기화 오류로 종료한다. 오류를 대화가 비었다는 뜻으로 해석하지 않는다. 크기 제한은 통신 계약과 경계 테스트로 양쪽에 일치시킨다.

### 8.3 수락, 동시 요청과 중복 방지

- PC와 앱의 새 일반 텍스트 요청은 Qt의 같은 수락 경계를 지난다. 기존 단일 작업 상태가 작업 중이면 추가 요청을 거절한다. 모바일용 숨은 대기열을 만들지 않는다.
- 모바일 전송마다 마지막 동기화에서 받은 `server_epoch`와 `conversation_id`를 포함한다. Qt가 요청을 실제 수락하기 직전에 현재 값과 비교하며, 불일치하면 기록 추가·AI 호출·기억 부수효과 없이 `stale_session`으로 거절하고 재동기화를 요구한다. 네트워크나 Qt 큐에서 지연된 요청도 예외가 아니다. 이전 대화에 속한 작업의 늦은 완료 콜백을 새 대화 기록에 반영하지 않는다.
- PC 입력 화면도 수락 결과를 받은 뒤 초안을 제거하도록 보완한다. 거절된 입력은 유지하고, 모바일에서 수락한 사용자 메시지는 PC에 한 번만 추가한다.
- 앱의 버튼 비활성화는 보조 UI다. 거의 동시인 요청도 서버 측 수락에서 한 건만 처리해야 한다.
- 기존 생활 기록 선행 처리처럼 한 건의 수락된 요청을 준비하는 과정은 `처리 준비 중`으로 표시한다. 이 준비 상태를 기록하고 요청 ID를 예약하되, 대화 기록 반영 전에는 최종 접수 확인을 보내지 않는다.
- 상태는 `접수 확인 중 → 처리 준비 중 → 접수 완료 → 응답 완료/실패`로 구분한다. 입력 검증·동시성 거절은 별도 결과다. `접수 완료`는 사용자 메시지가 PC 기록에 반영되었다는 의미이며 AI 응답 성공을 보장하지 않는다.
- `(등록 세대, server_epoch, conversation_id, request_id)`와 본문 해시로 중복을 판별한다. 재접속 후에도 같은 대화 동안 처리 상태를 유지한다.
- 원장은 Qt의 수락 경계에서 요청 예약·기록 반영·완료 상태와 함께 갱신한다. 게이트웨이 종료·재생성, 소켓 교체, 대화 요약은 원장을 초기화하지 않는다. 게이트웨이 세대와 소켓 ID는 중복 판별 키에 넣지 않는다. 같은 등록·실행·대화로 재접속하면 준비 중 요청까지 이전 상태를 조회한다.
- 동일 ID·동일 본문은 이전 상태를 돌려주고 AI를 다시 부르지 않는다. 동일 ID·다른 본문은 충돌 오류다. 접수된 기록을 살아 있는 대화 중에 조용히 만료시키지 않는다.
- 게이트웨이 종료는 Qt에서 해당 게이트웨이 세대의 신규 접수를 먼저 차단·무효화한 뒤 완료를 확인한다. 아직 Qt에서 수락·예약되지 않은 구세대 요청은 늦게 도착해도 부수효과 없이 거절한다. 차단 전에 예약·수락한 작업은 PC에서 계속 처리하고 원장을 갱신하며, 새 게이트웨이에서 같은 ID로 확인해도 다시 실행하지 않는다. 재시작은 새 게이트웨이 세대를 사용한다.
- 앱의 전송 도중 연결이 끊기면 먼저 전체 동기화와 미확정 요청 상태를 확인한다. 같은 실행·대화 안에서만 같은 ID로 안전하게 재시도할 수 있다. 이미 접수된 메시지는 다시 실행하지 않는다.
- PC 재시작·대화 초기화·기기 교체가 확인되면 이전 미확정 요청을 자동 재전송하지 않는다. 살아 있는 앱의 초안을 유지하고 사용자가 다시 전송할 수 있게 한다. 프로세스 종료를 넘어선 정확히 한 번 실행은 V1에서 보장하지 않는다.
- 최초 시도에서 확정적으로 거절된 뒤 사용자가 다시 전송하면 새로운 요청 ID를 사용한다. 응답 실패를 자동 재호출하거나 새 사용자 메시지로 중복 추가하지 않는다.

### 8.4 구버전 APK와 확장 호환성

- 같은 텍스트 계약을 유지하는 PC의 기분·기억·답변 생성 로직 변경은 기존 APK 수정 없이 활용할 수 있어야 한다. 이는 해당 기능이 기존 채팅 처리 경로로 제공될 때의 보장이지, 새로운 모바일 화면·명령까지 자동 생성한다는 뜻이 아니다.
- 인증 과정에서 선택적인 지원 기능 목록 `capabilities`를 교환한다. 목록이 없거나 비어 있으면 기본 텍스트 V1만 지원하는 것으로 처리한다. V1에는 음성·캐릭터·설정 편집 기능을 선언하지 않으며, 확장 메시지는 양쪽이 공통으로 지원한다고 확인한 경우에만 보낸다.
- 기존 필수 필드·의미·메시지 종류는 그대로 유지한다. 알려진 메시지에 추가된 선택 필드는 크기·구조 제한 안에서 무시할 수 있게 하되, 필수 필드 누락·잘못된 자료형·알 수 없는 명령을 성공으로 처리하지 않는다. 호환되지 않는 변경은 새 계약 버전으로 분리하고, 지원하지 않는 조합은 업데이트 안내로 종료한다.
- 향후 음성·캐릭터 전용 이벤트는 기본 대화의 `event_seq`를 소비하지 않는다. 확장 미지원 앱에 번호 누락이나 잘못된 대화 완료 상태를 만들지 않는다. 기본 기록의 의미를 바꾸는 변경을 무시 가능한 확장으로 숨기지 않는다.
- 두 저장소에 고정한 V1 가상 계약 데이터를 유지하고, PC 확장 시에도 기본 기능만 선언한 구버전 클라이언트의 인증·전체 동기화·전송이 통과하는지 검증한다. V1에서 범용 플러그인 구조나 동적 화면 생성기를 만들지는 않는다.

## 9. Android 수명과 오류 처리

- 앱이 활성 상태일 때 연결하고, 백그라운드에서는 지속 연결을 보장하지 않는다. 다시 열면 이전 소켓의 연결됨 표시를 신뢰하지 않고 새 연결로 인증과 전체 동기화를 수행한다. 완료 전에는 전송을 비활성화한다.
- 화면 회전은 같은 ViewModel을 사용한다. 프로세스 재생성 시 인증 설정만 복원하고 대화·초안은 새로 시작한다.
- 연결 상태는 미등록, 연결 중, PC 승인 대기, 동기화 중, 연결됨, 재연결 중, 조치 필요로 구분한다. 동기화 완료 전에는 전송을 활성화하지 않는다.
- 전송할 수 없을 때도 초안 작성은 허용한다. 연결 종료를 오프라인 전송 예약으로 취급하지 않는다.
- 재시도 간격은 작은 지터를 포함한 1·2·4·8·16·30초 상한으로 늘린다. 정상 동기화 후 초기화한다. 즉시 재시도 버튼은 기존 시도를 취소·대체한다.
- 재시도와 연결 단절 감지는 별개다. 인증된 일반 연결의 양쪽은 15초마다 앱 수준 생존 확인 요청을 보내고, 같은 식별자의 응답이 10초 안에 오지 않으면 해당 소켓을 닫는다. 정상적으로 실행 중인 앱은 재연결 상태로 전환하고 전송을 막는다. 단조 시간과 연결 세대별 타이머를 사용하고, 다른 데이터 수신으로 응답 기한을 계속 연장하거나 이전 소켓의 응답을 인정하지 않는다.
- 생존 확인은 대화 이벤트 번호·원장·AI 작업을 변경하지 않으며, 긴 스냅샷 전송 중에도 제어 메시지를 처리한다. 정상적으로 타이머가 실행되는 전경 환경에서 무응답 단절을 약 25초 이내에 감지하는 것이 기준이다. OS에 의한 백그라운드 정지에는 이 시간 보장을 적용하지 않고 앱 복귀 시 새 연결로 검증한다. WebSocket 라이브러리의 자동 응답이나 종료 콜백만으로 이 규칙을 대체하지 않는다.
- 주소마다 제한 시간을 적용한다. 모두 실패하면 저장한 인증정보를 유지하며 PC 실행·주소·개인 방화벽·공유기 기기 격리를 확인하도록 안내한다. 시간 초과만으로 특정 원인을 단정하지 않는다.
- QR 만료·거절은 새 등록으로, 인증 폐기는 미등록으로, 버전 불일치는 업데이트 안내로 이동한다. 이런 오류를 무한 재시도하지 않는다.
- 필요한 카메라·LAN 권한을 거부한 경우 해당 기능과 안내를 제공하고 요청 창을 반복하지 않는다. Android 17/target 37 이상에서는 직접 LAN 접속의 `ACCESS_LOCAL_NETWORK` 권한 처리를 포함한다. 낮은 target에서 불필요하게 이 권한을 요구하지 않는다. 실제 SDK 조합은 구현 계획에서 고정하고 그 조합으로 권한 거부·복구를 검증한다. [Android LAN 권한 문서](https://developer.android.com/privacy-and-security/local-network-permission)
- 모바일 서버만 실패하면 PC ENE는 계속 동작하며 오류와 재시작 동작을 표시한다. 서버 종료 시 Qt의 게이트웨이 세대 무효화·새 접수 차단 확인, 승인 대기 취소, 소켓 종료, 루프·스레드 정리 순서로 처리한다. 요청 원장은 유지하며, 실패 경로의 늦은 요청도 같은 세대 검증을 거친다.
- 시작 실패·종료 직전 콜백·늦은 이전 연결 콜백도 현재 상태를 덮어쓰지 않는다. 서버를 연속 시작해 두 포트 리스너나 두 작업 스레드를 만들지 않는다.

## 10. 입력 제한과 개인정보

- JSON 구조·문자열 길이·메시지 종류·프로토콜 버전을 검증한다. 잘못된 입력은 클라이언트 오류로 종료하고 ENE 예외로 전파하지 않는다.
- 인증 실패와 페어링 시도에는 주소별 및 전체 요청 제한을 둔다. 승인 대기는 한 건이며 과도한 인증 전 연결을 제한한다. IP 차단을 주 인증 방식으로 사용하지 않는다.
- 네이티브 클라이언트에서 필요하지 않은 브라우저 Origin 요청을 거부하며 무조건적인 CORS 허용을 사용하지 않는다. Origin 검사는 토큰 인증을 대체하지 않는다.
- 앱·서버의 신규 로그에는 실제 대화, 프롬프트, 인증정보, QR 원문을 출력하지 않는다. 검증 실패 로그에도 원본 페이로드를 붙이지 않는다.
- PC 등록 파일은 실행 데이터 전용 위치에 두고 Git에서 제외한다. API 키, 기억·프로필·설정 파일을 코드나 APK에 포함하지 않는다.
- 모든 테스트·문서 예시는 새로 만든 가상 데이터만 사용한다. 단말 검증도 가상 대화로 진행하고 수집한 화면·로그를 소스에 넣지 않는다.

## 11. 구현 순서와 검증 기준

현재 명세·계획 작성은 순차 직접 작업으로 진행한다. 실제 구현은 통신 계약을 먼저 고정하고 의존성 순서대로 진행한다. 별도 리뷰는 의미 있는 통합 체크포인트에 집중한다.

1. 통신 계약·상태 모델과 `ENE_APP` 최소 프로젝트 작성 → 검증: Python·Kotlin에서 동일한 가상 계약 데이터 해석, 기본 기능만 지원하는 조합, 버전·잘못된 입력 거절, 최소 APK 빌드.
2. PC 게이트웨이·로컬 승인 UI와 앱의 최소 연결 흐름 작성 → 검증: 실제 루프백 소켓, QR·승인·인증·만료, 주소 후보, 생존 확인, 재연결. 이 단계는 가상 대화 어댑터를 사용하고 실제 AI·기억에 연결하지 않는다. 임시 어댑터는 테스트·개발 진입점에만 두며 배포 경로에 남기지 않는다.
3. 조기 실기기 연결 체크포인트 → 검증: 실제 Android + 개인 LAN에서 QR·PC 승인·가상 메시지 왕복·재접속. 방화벽·주소·권한 문제를 실제 ENE 대화 통합 전에 확인한다. 실제 단말 접근이 없으면 이 항목을 미검증으로 기록하고, 통합 확대 전에 사용자와 검증 일정을 정한다.
4. PC 표시 기록·수락 경계·요청 원장 연결 → 검증: 요약 후 전체 기록 유지, PC 입력 거절 시 초안 유지, 오래된 편집·리롤 대상 거절, TTS·초기화 일치, 게이트웨이 재시작과 원장 유지. 핵심 대화·수명 경계 변경이므로 관련 회귀 및 전체 테스트 체크포인트.
5. 앱 대화 UI·수명 처리 완성과 실제 PC 통합 → 검증: 부분 스냅샷·화면 회전·키 복구·권한, 양방향 메시지, 처리 중 재연결, 동일 ID 재전송, PC와 앱 동시 입력, 세션 교체. 두 저장소 전체 테스트와 통합 리뷰 체크포인트.
6. 최종 실제 Android + 개인 LAN 인수 시험 → 검증: 아래 필수 시나리오와 서명된 설치용 APK. 조기 가상 메시지 시험은 실제 ENE 통합 검증을 대체하지 않는다. 실제 단말 접근이 없으면 해당 항목은 미검증으로 명시하고 완료 처리하지 않는다.

| 오래된 PC 편집·리롤 | PC 편집창을 연 뒤 모바일 새 대화가 완료되어도 저장 시 다른 메시지를 바꾸지 않고 거절·초안 유지. 지연된 리롤도 대상·개정 불일치 시 부수효과 없이 거절 |
| 주소·포트·권한 오류 | 두 번째 주소 성공과 후보 보존, 포트 충돌 표시, 권한 거부 후 복구 가능 |
| 서버 수명 | 연속 시작·종료 20회 및 ENE 종료에서 남은 리스너·스레드와 이전 콜백 영향 없음 |
| 확장 호환성 | 지원 기능 목록 누락·빈 목록과 선택 필드 추가에도 기본 텍스트 V1 정상 동작. 미지원 확장 이벤트 미전송·기본 이벤트 번호 연속성 유지, 필수 계약 위반은 명확히 거절 |
| 비밀정보·산출물 | 가상 데이터 기준 로그·저장소·APK에서 대화 파일·토큰 원문·제공자 키 미포함 |

테스트 통과와 실제 단말 인수 결과를 별도로 기록한다. 빌드 성공이나 문자열 존재 검사만으로 LAN 연결 성공을 주장하지 않는다. Critical·Important 문제는 즉시 해결하고 Minor 문제는 최종 리뷰에서 모아 판단한다.

## 12. 향후 확장 원칙과 추가 구현 경계

이 절은 확장을 막지 않기 위한 경계와 향후 검토 기준이다. 음성·Live2D·기분 표시·원격 설정을 V1에 구현하거나 검증 완료로 간주하지 않는다. 각 기능은 별도 설계·승인·PC와 APK 구현·실기기 검증이 필요하다.

### 12.1 PC 변경과 APK 변경의 구분

| 변경 종류 | APK 추가 작업 기준 |
| --- | --- |
| 기분·성격·기억 로직이 기존 텍스트 답변에 영향을 줌 | 기본 채팅 계약과 처리 경로를 유지하면 불필요 |
| 기분 수치·상태 표시, 새로운 버튼·명령·설정 화면 | 해당 표시·조작 및 통신 지원을 APK에 추가해야 함 |
| TTS·Live2D·쓰다듬기의 최초 모바일 지원 | PC 전달·수락 경로와 APK 재생·렌더링·입력 처리가 모두 필요 |
| 지원 완료된 기능의 음성 제공자·모델 데이터·설정값 변경 | 기존 음성 형식·모델 규격·설정 계약 안에서는 재빌드 없이 반영하도록 설계 가능. 새 해석 로직이 필요하면 APK 업데이트 필요 |

APK를 앞으로 전혀 수정하지 않는다는 보장은 하지 않는다. PC 업데이트만으로 활용할 수 있는 내부 기능과, 앱이 새로 이해·표현해야 하는 기능을 구분한다. 두 저장소의 배포 버전이 같을 필요는 없지만 지원하는 통신 계약 조합은 명시한다.

### 12.2 음성 출력

- PC가 생성한 음성을 모바일에 전달하고 앱이 재생하는 방식을 우선 검토한다. 같은 답변을 휴대폰에서 별도로 AI·TTS 호출하지 않는다. 현재 PC의 오디오·브라우저 재생 경로별로 전송 가능한 음성을 확보할 수 있는지 확인해야 한다.
- 텍스트 메시지와 음성의 식별자 연결, 음성 형식·크기·버퍼 제한, 취소·중단·재접속 시 과거 음성 재생 정책을 별도 계약으로 정한다. 모바일의 재생 실패가 이미 완료된 답변을 재생성하게 해서는 안 된다.
- 립싱크는 PC에서 신호를 받은 시각이 아니라 해당 기기의 실제 음성 재생 위치에 맞춘다. PC만·폰만·양쪽 재생 중 어떤 정책을 제공할지, 백그라운드 재생과 오디오 캐시의 수명은 해당 단계에서 결정한다.

### 12.3 Live2D와 상호작용

- 폰에는 모델 렌더러와 호환되는 모델·표정·동작 파일이 필요하다. PC 로컬 파일 경로를 그대로 보내는 것으로 해결하지 않는다. 모델 식별자·버전, 제한된 파일 전달·캐시, 호환성 및 배포 가능한 자산 범위를 별도 설계한다.
- 기분·쓰다듬기 횟수·공통 모델 설정의 원본은 PC가 소유한다. 폰의 쓰다듬기는 명시적인 상호작용 요청으로 PC에 전달하고 PC에서 한 번만 반영한 뒤 결과를 양쪽에 보낸다. 재접속 중복·구세션 요청 차단을 포함하며 PC의 임의 메서드를 호출하는 통로로 확대하지 않는다.
- 양쪽에서 공통 설정을 편집할 경우 PC가 모델·파라미터·값 범위·예상 개정을 검증하고 저장한 뒤 확정값을 배포한다. V1의 게이트웨이가 PC 설정 파일 전체를 내보내거나 수정하게 만들지 않는다. 화면 배치·확대율처럼 기기 화면에 종속된 설정은 공통 설정과 구분한다.
- 같은 기분·모델·설정·상호작용 결과 공유를 목표로 하되, 독립 렌더링의 모든 프레임·눈깜빡임·물리 계산 결과까지 같다고 보장하지 않는다. 동작 시작 시점의 동기화 수준은 후속 설계에서 정하고, 화면 스트리밍은 별개의 접근으로 취급한다.
- 렌더러는 Kotlin에서 사용하는 Cubism SDK와 기존 PC 웹 동작을 재사용하는 캐릭터 전용 WebView 방식을 비교한다. 전자는 Android 실행부를 별도 구현해야 하고, 후자는 PC의 Qt 연결부 분리·터치 변환·단말 성능 검증이 필요하다. Compose 기반 연결·채팅을 유지하면서 캐릭터 영역만 WebView로 구성하는 선택도 가능하다. V1에서 렌더러를 미리 확정하거나 PC 웹 코드를 대규모 분리하지 않는다. [Live2D SDK 문서](https://www.live2d.com/en/sdk/about/), [Compose와 Android View 통합 문서](https://developer.android.com/develop/ui/compose/migrate/interoperability-apis/views-in-compose)

### 12.4 외부 접속

Tailscale 등 사용자 설치형 연결 수단은 V1 구현·설정·검증 대상이 아니다. 호스트·포트와 실제 네트워크 도달 가능성으로 연결하는 현재 경계는 유지한다. 향후 별도 설치만으로 항상 접속된다고 보장하지 않으며 주소·방화벽 등 환경 설정이 추가로 필요할 수 있다.

## 13. 다음 단계

이 문서의 통합 검토가 끝나면 구체적인 파일별 구현 계획을 작성한다. SDK·의존성 버전, 메시지 스키마의 정확한 필드·크기 상한, 집중 테스트 명령과 통합 체크포인트는 구현 계획 및 계약 파일에서 고정한다. 승인된 기능 범위를 추가 질문으로 다시 열지 않는다.

전송 암호화는 부속 명세 검토 후 현재 V1 구현 계획에 선행 작업으로 반영한다. 2026-09-16 결정으로 음성·캐릭터 확장의 설계와 자동 검증 가능한 구현은 실기기 인수 전에 진행할 수 있다. 실제 단말 인수 의무가 사라지는 것은 아니며, 외부 접속은 계속 별도 범위다.

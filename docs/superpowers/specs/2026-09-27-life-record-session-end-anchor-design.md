# 생활 기록 세션 종료 기준점 수정 설계

## 1. 목표

승인·저장된 요약을 포함한 세션이 끝난 시각을 생활 기록의 단일 시작 기준으로 사용한다. 설정한 최소 시간도 세션 종료 시각부터 계산하고, 생성되는 기록의 `inactive_started_at`과 안정 ID도 같은 시각을 사용한다.

예를 들어 요약이 19:00에 저장되고 세션이 20:00에 끝났으며 최소 시간이 300분이면, 생활 기록은 다음 날 01:00 이후 빈 대화로 시작한 실행의 첫 일반 메시지에서만 생성할 수 있다. 생성되는 기록 구간도 20:00부터 시작한다.

## 2. 현재 문제와 원인

현재 V2 세션 상태는 활성 기준점에 요약 저장 시각 `saved_at`과 원본 세션 종료 시각 `origin_session_ended_at`을 모두 보관한다. 그러나 `AppSessionTracker._candidate_from_previous()`가 후보의 `started_at`으로 `saved_at`을 선택한다. 이후 게이트의 경과 시간 계산, 생성 프롬프트의 구간 시작, 저장 기록의 `inactive_started_at`이 모두 이 후보를 사용하므로 실제 동작은 요약 저장 시각 기준이 된다.

설계 문서와 테스트도 이 동작을 명시적으로 고정하고 있어 안내 문구만 바꾸는 수정으로는 해결되지 않는다.

## 3. 확정 동작

### 3.1 기준점 생성과 사용

1. 사용자가 요약을 승인하고 실제 기억 저장과 세션 tracker 등록까지 완료한다.
2. 그 요약을 포함한 세션이 정상 종료되거나 다음 시작에서 비정상 종료로 복구되면 활성 기준점을 만든다.
3. 활성 기준점의 생활 기록 시작 시각은 `origin_session_ended_at`이다.
4. 최소 시간은 `origin_session_ended_at`부터 첫 일반 메시지 수신 시각까지 계산한다.
5. 조건을 충족한 빈 실행의 첫 일반 메시지에서 생활 기록을 먼저 만들고 이어서 일반 답변을 만든다.
6. 새 기록의 `inactive_started_at`과 안정 ID 계산 시작점도 `origin_session_ended_at`이다.

정상 종료에서는 `origin_session_ended_at`이 종료 commit의 canonical `shutdown_at`이다. 비정상 종료 복구에서는 이전 실행의 마지막 유효 heartbeat인 `last_seen_at`을 종료 시각으로 사용한다. 기존 시간 순서 불변조건 `origin_session_started_at <= saved_at <= origin_session_ended_at`은 유지한다.

### 3.2 요약 없는 중간 세션

요약을 저장하지 않은 세션은 활성 기준점을 새로 만들거나 기존 기준점의 시각을 변경하지 않는다.

- 기존 활성 기준점이 없으면 계속 없는 상태다.
- 기존 미사용 기준점이 있으면 `saved_at`과 `origin_session_ended_at`을 그대로 보존한다.
- 그 실행에서 일반 메시지를 보내면 실행 단위 `life_gate_open`만 닫힌다. durable 기준점은 소비되지 않는다.
- 요약 없이 종료해도 기존 기준점은 그대로 남으며, 이후 조건을 충족한 빈 실행에서 다시 평가한다.
- 새 승인 요약이 있는 세션이 끝났을 때만 기존 미사용 기준점을 새 기준점으로 교체한다.
- 생활 기록 저장과 claim 완료가 모두 성공했을 때만 기준점을 소비한다.

### 3.3 설정 문구

라벨은 기준 시각을 정확히 드러내도록 다음 의미로 바꾼다.

- 한국어: `세션 종료 후 최소 시간:`
- 영어: `Minimum time after session end:`
- 일본어: `セッション終了後の最小時間:`

한국어 설명은 다음 문장을 기준으로 번역한다.

> 승인·저장된 요약이 있는 세션이 종료된 시점부터 이 시간이 지난 뒤, 빈 대화로 시작한 다음 실행의 첫 일반 메시지에서 생활 기록을 만듭니다.

## 4. 구현 설계

### 4.1 후보와 게이트

`AppSessionTracker._candidate_from_previous()`는 `InactiveStartCandidate.started_at`을 `active_anchor.origin_session_ended_at`으로 만든다. 미래 시각 검사도 이 종료 시각을 대상으로 한다.

`LifeRecordBridgeMixin`은 이미 `candidate.started_at`과 요청 수신 시각의 차이로 임계값을 계산하고, 같은 후보를 생성 context에 전달한다. 따라서 별도의 이중 기준을 추가하지 않고 후보의 의미만 바로잡는다.

### 4.2 안정 ID와 claim

새 generation claim의 `expected_record_id`는 다음 값으로 계산한다.

```text
stable_life_record_id(active_anchor.origin_session_ended_at, returned_at)
```

저장되는 기록도 같은 종료 시각을 `inactive_started_at`으로 사용하므로 claim과 권위 기록의 ID가 일치한다. claim 시간 순서 하한은 기존처럼 `saved_at`, `origin_session_ended_at`, 현재 세션 시작과 마지막 heartbeat 중 가장 늦은 시각을 사용한다.

### 4.3 기존 V2 claim 호환

이전 릴리스는 claim ID를 `stable_life_record_id(active_anchor.saved_at, returned_at)`으로 만들었다. 업데이트 시 이 claim을 곧바로 손상 상태로 판정하면 중단 복구가 읽기 전용으로 막힐 수 있다.

V2 parser는 이미 저장된 claim에 한해 다음 두 결정적 ID 중 하나를 허용한다.

1. 구버전 ID: `stable_life_record_id(saved_at, returned_at)`
2. 새 ID: `stable_life_record_id(origin_session_ended_at, returned_at)`

시작 복구는 저장된 `expected_record_id` 그대로 `life_records.json`과 대조한다. 기록이 있으면 기존 기준점을 소비하고, 없으면 claim만 해제한다. 이후 새 claim은 종료 시각 기반 ID만 생성한다. 스키마 버전은 V2로 유지하며 임의의 제3 ID는 계속 거부한다.

기존에 저장까지 끝난 생활 기록과 그 ID는 다시 쓰지 않는다. 최신 기록 재생성도 원래 기록의 `inactive_started_at`을 유지한다.

## 5. 오류 처리와 불변조건

- 종료 시각이 현재 요청보다 미래이면 후보를 만들지 않고 기존 fail-closed 진단을 유지한다.
- tracker 읽기·검증·commit 실패는 일반 대화를 유지하고 생활 기록 쓰기만 닫는 기존 정책을 유지한다.
- 생성·검증·기록 저장 실패는 새 종료 시각 기준점을 소비하지 않는다.
- 설정 시간이 되기 전에 첫 일반 메시지를 보내면 그 실행의 gate만 닫고 기준점은 다음 빈 실행까지 보존한다.
- 도구 명령, 입력 검증 단계의 거부와 일반 대화 commit rollback은 gate나 기준점을 소비하지 않는다.
- claim 저장에 실패한 요청을 일반 대화로 처리해 commit까지 성공하면 그 실행의 gate는 닫되 durable 기준점은 보존한다. 일반 대화 commit도 실패하면 gate를 유지한다.
- claim 해제 또는 소비 commit이 실패하면 디스크의 claim과 기준점을 그대로 보존하고 생활 기록 쓰기를 읽기 전용으로 닫는다.
- 요약 원문, 실제 대화와 사용자 개인정보는 로그·테스트·문서 예시에 넣지 않는다.

## 6. 테스트 전략

다음 회귀 테스트를 먼저 실패시키고 최소 구현으로 통과시킨다.

1. 요약 저장 19:00, 정상 종료 20:00이면 후보 시작이 20:00이다.
2. 같은 조건과 300분 설정에서 00:59에는 생성하지 않고, 이후 빈 실행의 01:00 첫 메시지에서 생성한다.
3. 생성 request, 저장 기록과 새 expected ID가 모두 20:00을 시작점으로 사용한다.
4. 비정상 종료 복구는 마지막 heartbeat를 동일한 시작점으로 사용한다.
5. 요약 없는 중간 메시지 세션과 종료가 기존 20:00 기준점을 이동하거나 소비하지 않는다.
6. 구버전 saved-at claim은 시작 시 기록 존재 여부에 따라 소비 또는 해제되고, 임의 ID는 거부된다.
7. 한국어·영어·일본어 설정 라벨과 설명이 세션 종료 기준을 명확히 표시한다.
8. 관련 세션 tracker, 게이트, E2E, 앱 lifecycle 집중 테스트를 실행하고 최종 체크포인트에서 전체 테스트를 실행한다.

## 7. 문서 변경

README 3개 언어, `docs/life_records.md`, 기존 2026-09-25 설계와 구현 계획에서 요약 저장 시각을 권위 시작점으로 설명한 부분을 새 세션 종료 기준으로 정정한다. 과거 문서를 삭제하지 않고 결정 변경임을 분명히 남겨 이후 구현자가 현재 동작을 잘못 복원하지 않게 한다.

## 8. 제외 범위

- 세션 종료 없이 실행 중 생활 기록을 생성하는 기능
- 요약 없는 세션 종료로 기준점을 갱신하는 기능
- 기존에 저장된 생활 기록의 구간이나 ID를 일괄 변환하는 기능
- 설정 시간 이전에 시작한 실행을 자동으로 재개하거나 알림을 보내는 기능
- 자동 요약 확인창의 UI 재설계

## 9. 결정 기록

- 기준점 자격: 승인·저장된 요약이 있는 세션만 생성
- 기준 시각: 해당 세션의 canonical 종료 시각
- 임계값 시작: 세션 종료 시각
- 기록 구간 시작: 세션 종료 시각
- 새 안정 ID 시작 인자: 세션 종료 시각
- 요약 없는 세션: 기존 durable 기준점 보존
- 구버전 claim: 저장된 두 결정적 ID만 호환
- 스키마: V2 유지

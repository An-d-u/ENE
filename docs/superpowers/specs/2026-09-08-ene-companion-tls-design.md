# ENE LAN 동반 앱 HTTPS/WSS 전환 설계

작성일: 2026-09-08

상태: 2026-09-08 사용자 진행 승인으로 인증서·복구 세부 설계 검토 완료. 구현 및 실기기 검증은 [TLS 구현 계획](../plans/2026-09-08-ene-companion-tls.md)에서 별도 추적한다.

## 1. 변경 범위와 선택 이유

[기본 V1 설계](2026-09-07-ene-companion-lan-v1-design.md)의 전송 보안만 확장한다. 같은 개인 LAN, 실행 중인 PC, Android 한 대, QR와 로컬 승인, 현재 대화 전체, 텍스트 전송, 독립 `ENE_APP/` 저장소를 유지한다. Tailscale·인터넷 공개·중계 서버·음성·Live2D·원격 설정은 추가하지 않는다.

비교한 접근은 다음과 같다.

- **PC 전용 CA와 서버 인증서 분리 — 선택:** QR에는 이 PC만 신뢰하는 공개 CA 인증서를 넣고 표준 TLS 체인·서버 이름 검증을 사용한다. PC에 인증서 두 종류를 관리하는 비용이 있지만 일상적인 서버 인증서 갱신 때 APK 교체나 재페어링이 필요 없다.
- 서버 인증서 하나를 QR에 직접 고정: 생성은 더 간단하지만 인증서 교체마다 재등록 규칙이 필요하고, 자체 서명 인증서를 신뢰 기준으로 쓸 때의 유효기간 검증까지 신중히 다뤄야 한다.
- 공인 인증서와 도메인: 일반 HTTPS 검증을 사용하기 쉽지만 도메인 소유·발급·갱신·LAN 이름 해석을 사용자 설치 과정에 추가한다. 현재 범위에 맞지 않는다.

메시지별 자체 암호화, 전송 키 협상 프로토콜, 범용 인증서 관리 서비스, 별도 CA 서버는 만들지 않는다. CA는 PC 내부의 인증서 발급용 키·인증서일 뿐 외부 서비스가 아니다. QR로 등록한 공개 인증서는 앱 전용 신뢰 저장소에만 적용하고 Android/Windows 시스템 인증서 저장소를 변경하지 않는다.

## 2. TLS 신원과 실제 주소의 분리

- 접속 가능한 실제 주소는 기존 `addresses:[{host,port}]`와 수동 주소 편집을 사용한다. QR은 IPv4 최대 8개, 수동 호스트는 기존 검증을 유지한다.
- TLS 서버 이름은 정규화된 UUID인 `server_id`로부터 `ene-<server_id>.invalid`를 결정적으로 만든다. 실제 사용자 이름·컴퓨터 이름·주소를 인증서에 기록하지 않는다.
- 앱 URL·SNI·인증서 SAN·기본 호스트 이름 검증에는 이 고정 이름을 사용한다. 연결 전용 DNS 매핑으로 이 이름만 선택한 실제 IPv4 주소에 연결한다. 고정 이름을 외부 DNS로 질의하거나, IP로 접속하기 위해 `HostnameVerifier`를 항상 성공하도록 바꾸지 않는다.
- 수동 DNS 호스트는 주소 후보를 얻기 위한 입력일 뿐 신뢰 기준이 아니다. 해석된 IPv4 후보마다 동일한 TLS 신원을 검증하며 기존 시간·후보 상한 안에서 시도한다. 잘못된 DNS 응답은 연결 실패를 만들 수 있지만 다른 PC에 자격증명을 보내는 근거가 되지 않는다.
- `/info`, `/pair`, `/ws` 모두 HTTPS/WSS만 제공한다. 경로와 기본 포트 8765는 유지한다. TLS 1.2 이상만 허용하고 TLS 1.3은 양쪽 런타임 지원 시 사용한다. 암호군을 자체 설계하지 않고 검증된 라이브러리의 안전한 설정을 사용한다.
- 리다이렉트·시스템 프록시·자동 자격증명 공급자·은밀한 라이브러리 재시도는 계속 끈다. 신뢰 대상이나 연결 세대가 달라지면 이전 클라이언트의 풀·소켓을 재사용하지 않는다.

이는 유료 도메인을 사용하는 구조가 아니다. `.invalid` 이름은 앱 내부 TLS 식별용이며 주소 탐색 기능을 추가하지 않는다. LAN 범위와 OS 방화벽 제한은 기존 설계대로 유지한다.

## 3. 인증서 생성·보관·갱신

- PC 설치마다 독립적인 ECDSA P-256 CA 키와 서버 키를 생성한다. 서명은 SHA-256을 사용한다. CA는 자체 서명, `BasicConstraints CA=true/pathLen=0`, 인증서 서명 용도를 가지며 중간 CA는 두지 않는다. 서버 인증서는 `CA=false`, `serverAuth`, 서명 용도와 고정 서버 이름 SAN을 가진다.
- CA 유효기간은 생성 시점부터 3,650일, 서버 인증서는 최대 90일이며 CA 만료를 넘지 않는다. 발급 시 `notBefore`에 5분의 여유만 둔다. 잘못된 단말 시계를 이유로 인증서 검증을 끄지 않는다.
- 서버 시작 전에 남은 서버 인증서 유효기간이 30일 이하이면 같은 CA로 새 서버 키·인증서를 발급하고 원자적으로 저장한다. 실행 중에도 수명 확인을 수행하여 같은 기준으로 갱신한다. 새 보관과 TLS 컨텍스트 준비가 성공한 뒤 기존 연결을 정리하고 새 리스너로 전환한다. 기존 QR·승인 대기는 취소하고 앱은 기존 등록으로 전체 재동기화한다.
- 일상 갱신은 CA와 `server_id`를 바꾸지 않고 기기 등록도 유지한다. 게이트웨이 재시작과 동일하게 Qt가 소유한 현재 대화·요청 원장은 유지하여 재접속이 중복 AI 실행을 만들지 않는다.
- 갱신 실패 시 기존 인증서가 아직 유효하면 제한된 재시도와 PC 조치 안내를 제공한다. 만료되면 새 연결과 기존 모바일 연결을 중단하며 PC 자체 기능은 유지한다. 무기한 재시도나 만료 인증서 사용, 평문 전환은 금지한다. CA 만료가 가까우면 아래의 로컬 초기화·재등록을 안내한다.
- CA 잔여 수명이 30일 이하이면 서버 인증서 자동 갱신 대신 로컬 초기화를 안내하고, 유효한 기존 인증서의 남은 기간에만 연결을 허용한다. CA 만료에 잘린 새 인증서를 반복 발급하여 연결을 계속 재시작하는 갱신 루프를 만들지 않는다.
- 개인키·인증서는 저장소 밖 앱 실행 데이터의 전용 디렉터리에 보관한다. Windows는 현재 사용자와 SYSTEM만 접근하는 상속 차단 DACL, POSIX 시험 환경은 디렉터리 0700·개인키 파일 0600을 적용하고 검증한다. 권한을 보장할 수 없으면 서버를 시작하지 않는다. 다른 사용자로 실행할 때 자동으로 권한을 넓히지 않는다.
- 신원 묶음의 생성·교체는 같은 보호 디렉터리 안에서 원자적으로 수행한다. 개인키를 쓰기 전에 디렉터리 접근 제한을 설정하고 교체 후에도 확인한다. 심볼릭 링크·재분석 지점과 예상 밖 대상 경로는 거절한다. 디스크의 개인키 보호는 OS 접근 제한이며 별도의 디스크 암호화를 제공한다고 표현하지 않는다.
- Python TLS 로더용 PEM이 필요하면 같은 보호 디렉터리 안의 제한된 임시 파일만 사용하고 성공·실패·재시작 정리 경로를 둔다. 일반 임시 폴더, 소스 경로, 로그, QR, APK, Git에 개인키가 남지 않게 한다. 초기화 시에도 사용자 폴더 전체를 지우지 않는다.
- 기존 등록이 있는데 CA 키·신원 묶음이 없거나 손상되었다면 새 CA를 자동 생성해 기존 등록과 이어 붙이지 않는다. 신원 보관과 등록에 기록된 CA 지문이 일치하지 않아도 인증을 차단하고 복구 안내를 한다.

CA 키를 분리하는 이유는 서버 인증서 갱신 때 신뢰 기준을 유지하기 위해서다. CA 키 탈취를 서버 키 탈취와 완전히 격리하는 오프라인 CA 보안을 제공하는 것은 아니다. 두 키는 같은 PC에서 관리된다.

## 4. QR 부트스트랩과 등록 저장

- 기존 QR 필드에 필수 `transport:"tls_v1"`, `ca_certificate`를 추가한다. `ca_certificate`는 공개 CA의 DER 바이트를 정규 base64로 인코딩한다. 개인키나 비밀번호는 포함하지 않는다.
- QR 전체 UTF-8 2 KiB, CA DER 768바이트, 주소 8개 한도를 유지한다. CA 인증서 생성 시 크기 상한을 보장하고 최장 허용 주소 조합으로 계약 테스트한다. 한도를 넘으면 조용히 필드를 생략하지 않고 QR 생성·읽기를 실패 처리한다.
- QR을 읽은 앱은 네트워크 접근 전에 기존 ID·만료·secret 검증과 함께 CA 파싱·단일 인증서·자체 서명·P-256·CA 용도·유효기간·상한을 검증한다. `transport` 또는 CA가 없으면 구형 페어링 정보로 거절한다.
- QR은 사용자가 신뢰하는 PC 화면에서 직접 스캔하는 별도 신뢰 경로다. 네트워크에서 처음 받은 인증서를 무조건 신뢰하는 방식이나 인증서 오류를 무시하고 비밀값을 보내는 부트스트랩을 만들지 않는다.
- 앱은 QR의 CA만 넣은 전용 trust store와 플랫폼 `TrustManagerFactory`로 체인을 검증하고 기본 서버 이름 검증을 유지한다. 시스템·사용자 설치 CA를 추가하지 않는다. 자체 인증서 무검증 구현이나 `CertificatePinner` 하나로 자체 서명 인증서의 신뢰가 자동 해결된다는 가정을 하지 않는다.
- 저장된 등록 복원과 매 연결 시도에도 CA 자체의 유효기간을 명시적으로 검사한다. 플랫폼이 신뢰 앵커의 만료까지 검사한다고 가정하지 않는다. 연결 중 CA 유효기간 종료 및 전경 복귀 때도 확인하여 만료된 신뢰 정보로 대화를 계속 전송하지 않는다. 신뢰 체인·서버 이름 검증에 실패한 연결을 이 검사만으로 허용하지 않는다.
- 익명 `/info` 조회도 위 TLS 설정을 사용한다. `server_id`와 지원 텍스트 버전을 확인한 뒤 실제 `/pair`와 `/ws` 연결에서도 같은 TLS 검증을 다시 거친다. 앞선 `/info` 성공만 믿고 다음 연결에 토큰을 먼저 전송하지 않는다.
- QR의 120초 수명·첫 요청 바인딩·PC 승인·기기 교체 장벽은 유지한다. 신뢰 기준을 등록했어도 PC 승인 전에는 대화를 읽거나 보낼 수 없다. 클라이언트 인증서를 추가하는 상호 TLS는 도입하지 않는다.
- PC 승인 성공 후 Android는 토큰·기기 식별자·등록 세대·`server_id`·전송 프로필·CA 인증서를 하나의 Keystore 암호화 등록 레코드로 원자 저장한다. 공개 CA와 토큰을 서로 다른 시점에 교체하지 않는다. 주소 목록은 비밀이 아닌 별도 설정으로 두되 등록의 PC ID와 일치해야 사용한다.
- 저장 전 실패·취소는 기존 등록을 덮어쓰지 않는다. PC 승인은 완료했지만 앱 저장·수신에 실패한 경우 성공으로 표시하지 않고 새 QR 등록을 요구한다. 그 경우 PC의 이전 기기 등록까지 유지되었다고 보장하지 않는다.
- QR 비밀값은 메모리에서만 처리하고 등록 완료·취소·만료 때 더 이상 참조하지 않는다. 토큰·CA·주소는 백업·기기 이전에서 제외한다. 실제 힙 전체에서 원문이 완전히 지워진다고 주장하지 않는다.

## 5. 오류와 재등록

- 전송 오류·시간 초과·CA/서버 이름 불일치에서는 기존 토큰과 신뢰 정보를 보존하되 해당 연결을 닫고 새 전송을 막는다. 제한된 다른 주소 후보 확인은 허용하지만 실패한 후보에 비밀값을 보내거나 받은 인증서로 신뢰 기준을 바꾸지 않는다.
- 후보 전체가 신원 검증에 실패하면 자동 반복 대신 조치 필요 상태로 전환한다. 인증서 만료·시계 오류·다른 PC 가능성을 구분 가능한 범위에서 안내하며 가짜 네트워크 응답으로 인증정보를 삭제하지 않는다.
- 토큰 폐기는 올바른 TLS 신원이 확인된 서버의 명확한 인증 거절일 때만 자동 반영한다. `401` 상태 코드만으로 삭제하지 않는다. TLS 검증 이전 실패에 서버 오류 본문을 신뢰하지 않는다.
- 새 CA로 바꿔야 하는 경우 PC 로컬의 명시적 인증 정보 초기화를 사용한다. 먼저 Qt 신규 접수 차단과 현재 연결·QR 종료, 기존 등록 폐기의 내구 확인을 완료한 다음 새 신원을 저장한다. 이후 QR·로컬 승인을 다시 수행한다. CA 키 재생성·등록 폐기를 원격 API로 노출하지 않는다.
- 초기화의 저장 결과가 불명확하면 차단 상태를 유지한다. 재시작 시 신원과 등록의 CA 지문 일치를 검사하여 중간 단계의 파일 조합을 정상 등록으로 사용하지 않는다. 기존 PC 대화·기억·설정은 지우지 않는다.
- 신뢰 정보가 없는 기존 개발용 토큰은 주소에서 인증서를 받아 자동 승격하지 않는다. 새 QR 등록을 안내한다. 이 전환으로 기존 개발 빌드의 페어링은 다시 해야 한다.

## 6. 호환 경계와 기존 코드 재사용

텍스트 계약의 `protocol_version = 1`, 이벤트·스냅샷·메시지·중복 방지 의미는 그대로 유지한다. TLS 전송 프로필은 협상 가능한 선택 기능이 아니라 이 V1의 필수 연결 조건이다. 배포되지 않은 평문 개발 빌드를 지원하기 위한 HTTP 리스너나 다운그레이드는 제공하지 않는다. 이후의 구버전 호환 보장은 `tls_v1`을 구현한 기본 텍스트 앱부터 적용한다.

재사용하는 영역은 PC 대화 기록·요청 원장·Qt 경계·로컬 승인, 앱 메시지 모델·스냅샷 조립·생존 확인·전경 재연결·대화 UI다. 변경하는 영역은 PC TLS 신원·서버 시작/갱신, QR 계약, 앱 TLS 클라이언트·주소 매핑, 등록 보관 형식과 오류 처리다.

현재 PC 작업 트리의 게이트웨이와 `ENE_APP/`의 부분 작성 전송 코드는 아직 평문 기반이다. 기존 테스트 통과는 TLS 동작의 증거가 아니다. [기존 구현 계획](../plans/2026-09-08-ene-companion-lan-v1.md)의 Task 5를 계속하기 전에 이 변경의 상세 TDD 작업을 삽입한다. 두 저장소의 계약 사본·테스트·설치 안내를 같이 갱신하고 Android 작업 영역은 옮기지 않는다.

## 7. 검증 기준

가상 데이터와 시험용으로 새로 생성한 인증 키만 사용한다. 실제 PC 등록·대화·기억·인증키를 시험 fixture나 공개 문서에 복사하지 않는다.

| 영역 | 통과 조건 |
| --- | --- |
| QR | 정상·오래된 QR·잘못된 CA·과대 DER·최장 주소 조합을 Python/Kotlin 공통 사례로 검증 |
| 암호화·신원 | 실제 TLS 소켓으로 `/info`·페어링·대화 성공, 평문·다른 CA·같은 CA의 다른 이름·만료/미래 인증서·TLS 1.0/1.1 거절 |
| 비밀값 미전송 | 잘못된 인증서의 시험 서버가 HTTP 헤더·QR 비밀값·토큰을 받지 않음. `/info` 이후 대상 교체·리다이렉트·풀 재사용도 검증 |
| 인증서 수명 | 재시작·IP/포트 변경·같은 CA의 서버 키/인증서 갱신에 새 APK/QR 불필요, 갱신 시 요청 원장·동기화 보존 |
| 장애 복구 | CA 손실/만료·시계 오류·보관 실패·권한 실패·초기화 도중 종료에서 차단 또는 명확한 재등록, 신뢰 자동 교체 없음 |
| 등록 원자성 | 서로 다른 CA의 토큰 혼합·저장 중 종료·승인 후 저장 실패를 정상 등록으로 사용하지 않음 |
| 자원·수명 | TLS 협상 무응답 timeout, 연결 폭주·갱신/종료 경합에서 작업/소켓 누적 방지. 기존 HTTP 단계 연결 제한만으로 TLS 이전 자원이 제한된다고 주장하지 않음 |
| 앱 정책·산출물 | Manifest/XML 및 실제 APK에 평문 허용·검증 우회·공통 개인키 없음, Keystore/백업 제외 유지 |
| 조기 실기기 | 기존 Task 6에서 실제 Android와 PC가 HTTPS/WSS로 QR→승인→가상 대화→재접속 성공 |

TLS 이전 연결은 핸드셰이크 제한 시간과 서버 연결 자원 제한을 별도로 검증한다. 제한을 라이브러리에서 구현할 수 없는 부분은 인수 기록에 잔여 위험으로 명시하고 LAN 방화벽을 대체한다고 주장하지 않는다. 외부에 공개하지 않는 정책은 계속 유지한다.

## 8. 실행 및 검토 경계

구현은 `Sequential direct implementation`으로 진행한다. 인증서 신뢰→보관→서버→앱→연동은 순차 의존성이 있어 구현 에이전트를 나누지 않는다. 보안 경계 변경에 대한 한 번의 집중 명세 리뷰를 수행하며 Task마다 별도 리뷰 연쇄를 만들지 않는다.

순서는 부속 명세 검토, 파일별 실패 테스트·구현 계획 보완, 순차 구현, 두 저장소의 집중 TLS 통합 검증, Task 5/6 재개다. 실제 단말이 없으면 자동 테스트 결과와 실기기 미검증을 분리한다. 변경 문서 검토가 끝나기 전에 앱을 암호화 완료로 표시하거나 평문 개발 빌드를 설치 가능한 완성본으로 인계하지 않는다.

집중 명세 리뷰 결과: 중대 누락·상충 없음. 권고된 CA 복원/재연결 시 만료 확인과 CA 만료 직전 반복 갱신 방지 규칙을 반영했다. 사용자 문서 검토 및 이후 상세 계획·코드·실기기 검증은 별도 단계다.

## 9. 확인 근거

- [Android TLS와 인증서 검증](https://developer.android.com/privacy-and-security/security-ssl): 신뢰 체인·서버 이름 검증, 무검증 TrustManager 금지. 특정 공개 서비스 인증서를 APK에 고정하는 방식의 갱신 문제와 PC별 QR 신뢰 등록을 구분한다.
- [Android 네트워크 보안 설정](https://developer.android.com/privacy-and-security/security-config): 앱 범위의 평문 차단과 신뢰 설정. 동적으로 QR에서 받은 CA는 APK의 정적 인증서 목록 대신 연결 전용 trust store로 적용한다.
- [OkHttp 5.3.2 DNS 인터페이스](https://raw.githubusercontent.com/square/okhttp/parent-5.3.2/okhttp/src/commonJvmAndroid/kotlin/okhttp3/Dns.kt): 고정된 서버 이름을 특정 접속 IP에 매핑하는 확장 지점.
- [Python SSL](https://docs.python.org/3/library/ssl.html): TLS 컨텍스트·최소 버전·인증서 체인 로딩. 실제 구현은 프로젝트 Python 3.11/3.12 공통 API로 확인한다.
- [Cryptography X.509](https://cryptography.io/en/latest/x509/tutorial/): CA·서버 인증서 생성 원리. 개발 문서의 버전을 그대로 설치하지 않으며 실제 패키지 버전·배포 호환성은 상세 구현 계획에서 고정한다.

PC별 CA와 고정 내부 이름의 조합, 수명 값과 복구 규칙은 위 API를 이용한 이 프로젝트의 설계 결정이다. 공식 문서가 이 제품의 전체 조합이나 실기기 호환을 보증하는 것은 아니다.

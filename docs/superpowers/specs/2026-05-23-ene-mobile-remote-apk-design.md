# ENE 모바일 원격 APK V1 설계

## 목표

컴퓨터에서 ENE 클라이언트가 켜져 있을 때, Android 폰에서도 같은 ENE를 사용할 수 있는 APK를 만든다.

V1의 목표는 다음과 같다.

- PC ENE를 대화, 기억, TTS, 상태 관리의 본체로 유지한다.
- Android APK는 PC ENE에 원격으로 붙는 모바일 클라이언트로 만든다.
- 폰에서도 Live2D, 채팅, PC 생성 TTS 재생, 표정, 립싱크를 제공한다.
- 대화 상황, 기억, 기분, 목표, 예정된 대화 약속은 PC ENE와 동일한 상태를 사용한다.
- 입력은 텍스트, 녹음 후 확인 전송, 파일 첨부를 지원한다.
- 설정 편집과 데스크톱 전용 기능은 V1 범위에서 제외한다.

## 배경

현재 ENE는 PyQt6 데스크톱 앱이다. `QWebEngineView`가 `assets/web/index.html`과 `assets/web/script.js`를 로드하고, Python의 `WebBridge`가 `QWebChannel`로 JavaScript와 통신한다.

기존 구조의 핵심은 다음과 같다.

- Live2D 렌더링과 채팅 UI는 웹 자산인 `assets/web`에 있다.
- 대화, 기억, 캘린더, 기분, 목표, 예정된 대화 약속은 Python 런타임에 있다.
- TTS 생성과 오디오 재생, 립싱크 이벤트는 `WebBridge`와 TTS 클라이언트가 담당한다.
- 설정과 비밀값은 사용자 데이터 디렉터리의 JSON 파일에 저장된다.

따라서 모바일 V1에서 LLM, 기억, TTS, 설정을 Android에 다시 구현하는 것은 비용이 크고 동기화 문제가 생긴다. V1은 PC ENE를 본체로 유지하고, APK는 원격 UI와 입력/출력 장치 역할을 맡는다.

## 범위

### 포함

- PC ENE 내부에 모바일 연결 서버 추가
- Android WebView 기반 APK 추가
- 기존 `assets/web` Live2D/채팅 UI를 모바일용으로 재사용하거나 얇게 분기
- PC와 APK 사이의 HTTP/WebSocket 기반 통신 규약 추가
- QR 페어링으로 접속 주소와 인증 토큰 등록
- Tailscale, Cloudflare Tunnel 같은 사용자 관리형 터널을 통한 외부 접속 지원
- 텍스트 메시지 전송
- 녹음 후 미리듣기, 다시 녹음, 전송
- 이미지, `txt`, `md`, `pdf`, `docx` 파일 첨부
- 모바일 첨부 파일 20MB 이하 제한
- PC 생성 TTS 오디오를 APK에서 재생
- 표정, 립싱크, mouth pose 이벤트를 APK에 전달
- PC의 대화 상태, 기억, 기분, 목표, 예정된 대화 약속 상태를 모바일에 반영
- 연결 상태, 인증 실패, PC 오프라인, 전송 실패에 대한 기본 UX
- 모바일 연결 관련 단위 테스트와 수동 검증 절차 추가

### 제외

- 자체 릴레이 서버 운영
- 폰 단독 LLM 실행
- 폰 단독 TTS 생성
- 모바일에서 전체 설정 편집
- 트레이, 창 위치, 마우스 추적, 데스크톱 화면 감지 같은 데스크톱 전용 기능
- Obsidian 패널 전체 이식
- 모바일에서 로컬 파일 시스템을 PC처럼 직접 조작하는 기능
- 다중 PC 계정 동기화
- 백그라운드 상시 실행 보장
- 앱스토어 배포 자동화

## 제품 방향

V1은 "폰에 독립 ENE를 새로 만드는 것"이 아니라 "PC ENE를 안전하게 들고 다니는 원격 클라이언트"다.

사용자는 PC에서 ENE를 켜고, 폰 APK를 열어 페어링한다. 이후 폰에서 메시지를 보내면 PC ENE가 기존 대화 흐름으로 처리하고, 결과 텍스트, 감정, TTS 오디오, 립싱크 이벤트를 폰으로 돌려준다.

이 방향의 장점은 다음과 같다.

- 이미 구현된 대화, 기억, TTS, Live2D 상태 흐름을 재사용한다.
- PC와 폰의 ENE가 서로 다른 기억을 갖는 문제를 피한다.
- APK 첫 버전의 범위를 출시 가능한 크기로 유지한다.
- 나중에 자체 릴레이 서버로 확장할 수 있는 통신 경계를 만든다.

## 접근 방식 비교

### 1. 터널 지원 + PC 호스트 + WebView APK

추천안이다. PC ENE에 모바일 연결 서버를 추가하고, APK는 WebView로 기존 Live2D/채팅 UI를 재사용한다. 외부망 접속은 사용자가 Tailscale, Cloudflare Tunnel 같은 검증된 터널을 구성해서 해결한다.

장점:

- V1 구현 범위가 가장 작다.
- 기존 ENE 상태와 기능을 가장 많이 재사용한다.
- 자체 서버 운영 전에도 외부 접속 사용성을 검증할 수 있다.
- 보안 책임을 터널과 앱 토큰으로 나눌 수 있다.

단점:

- 사용자가 터널 도구를 설치하거나 설정해야 한다.
- 네트워크 경로가 사용자 환경마다 달라 온보딩 문서가 중요하다.

### 2. 자체 릴레이 서버 포함

PC ENE와 APK가 모두 ENE 릴레이 서버에 접속하고, 서버가 메시지를 중계한다.

장점:

- 제품 관점에서 가장 매끄럽다.
- 사용자가 별도 터널 도구를 몰라도 된다.

단점:

- 서버 운영, 인증, 암호화, 비용, 장애 대응이 필요하다.
- 개인 대화와 오디오가 중계되므로 보안 책임이 커진다.
- V1 구현 범위가 과도하게 커진다.

### 3. 폰 독립 ENE

Android가 LLM, 기억, TTS, Live2D, 설정을 독립적으로 실행하고 PC와 상태를 동기화한다.

장점:

- PC가 꺼져 있어도 일부 기능을 사용할 수 있다.

단점:

- "컴퓨터 ENE와 그대로 연결"이라는 요구와 맞지 않는다.
- 기억, 대화 세션, TTS 설정, 파일 상태 동기화가 매우 복잡하다.
- V1로는 반대한다.

## V1 결정

V1은 1번 접근을 사용한다.

```text
Android APK
→ WebView Live2D/채팅 UI
→ HTTP(S)/WebSocket
→ 사용자 관리형 터널
→ PC ENE 모바일 연결 서버
→ 기존 WebBridge/LLM/Memory/TTS 흐름
```

## 아키텍처

### PC ENE 모바일 연결 서버

PC 앱 내부에 모바일 연결 서버를 추가한다. 서버는 ENE 앱이 실행 중일 때만 열린다.

책임:

- 페어링 QR 생성
- 인증 토큰 검증
- 모바일 세션 관리
- 모바일 메시지 수신
- 모바일 첨부 파일 수신
- 모바일 녹음 파일 수신
- 기존 `WebBridge` 대화 흐름으로 요청 전달
- 응답 텍스트, 감정, 생각, 기분, 목표, 예정 목록 이벤트 전송
- PC 생성 TTS 오디오와 립싱크 이벤트 전송
- 연결 상태와 오류 이벤트 전송

구현 후보:

- Python 표준 HTTP 서버는 WebSocket과 파일 업로드에 불편하므로 V1 기본안으로 쓰지 않는다.
- 이미 의존성에 있는 `aiohttp`를 우선 사용한다.
- 서버는 별도 스레드 또는 별도 asyncio 루프에서 실행하고, Qt 객체 변경은 Qt 스레드로 안전하게 넘긴다.

### Android APK

APK는 WebView 기반 앱이다.

책임:

- 모바일 전용 진입 화면과 페어링 화면 제공
- QR 코드 스캔 또는 수동 주소/토큰 입력
- 인증 토큰을 Android 안전 저장소에 저장
- WebView에서 Live2D와 채팅 UI 표시
- PC 서버와 WebSocket 연결 유지
- 텍스트, 녹음, 파일 첨부 전송
- PC에서 받은 TTS 오디오 재생
- PC에서 받은 표정과 립싱크 이벤트를 Live2D에 적용
- 네트워크 끊김, 인증 실패, PC 오프라인 상태 표시

기술 선택:

- V1은 WebView 기반을 사용한다.
- V1 Android 프로젝트는 Capacitor 기반으로 만든다.
- 기존 웹 자산 재사용, 권한 플러그인, APK 빌드 흐름을 얻기 위해 순수 Android 네이티브 WebView보다 Capacitor를 우선한다.
- Android 네이티브 코드는 QR 스캔, 안전 저장소, 파일 선택, 녹음 권한처럼 Capacitor 기본 기능만으로 부족한 부분에 한정한다.

## 통신 규약

PC와 APK는 HTTP와 WebSocket을 함께 사용한다.

HTTP:

- 상태 확인
- 페어링
- 파일 업로드
- 녹음 업로드
- TTS 오디오 조각 다운로드가 필요한 경우의 폴백

WebSocket:

- 채팅 메시지 이벤트
- 응답 텍스트 이벤트
- 표정 이벤트
- 립싱크 이벤트
- TTS 시작, 청크, 종료 이벤트
- 기분, 목표, 예정 목록 갱신 이벤트
- 오류와 연결 상태 이벤트

초기 엔드포인트 후보:

```text
GET  /mobile/health
POST /mobile/pair/start
POST /mobile/pair/confirm
GET  /mobile/session
POST /mobile/attachments
POST /mobile/recordings
GET  /mobile/ws
```

WebSocket 이벤트 후보:

```json
{
  "type": "chat.send",
  "client_message_id": "msg_...",
  "text": "안녕",
  "attachment_ids": []
}
```

```json
{
  "type": "chat.response",
  "client_message_id": "msg_...",
  "text": "어서 와요.",
  "emotion": "smile",
  "thought": ""
}
```

```json
{
  "type": "tts.audio",
  "format": "wav",
  "sequence": 1,
  "data_base64": "..."
}
```

```json
{
  "type": "live2d.mouth_pose",
  "payload": {
    "source": "viseme",
    "open": 0.42,
    "jaw": 0.21,
    "form": 0.1
  }
}
```

세부 필드명은 구현 계획에서 테스트와 함께 고정한다.

## 페어링과 인증

V1은 QR 페어링을 사용한다.

흐름:

```text
PC ENE 설정 또는 트레이 메뉴에서 "모바일 연결" 열기
→ PC가 1회용 페어링 토큰과 접속 URL을 만든다
→ QR 코드 표시
→ APK가 QR을 스캔한다
→ APK가 /mobile/pair/confirm 호출
→ PC가 장기 인증 토큰을 발급한다
→ APK가 장기 토큰을 안전 저장소에 저장한다
→ 이후 WebSocket/HTTP 요청마다 토큰을 보낸다
```

보안 규칙:

- 페어링 토큰은 짧은 만료 시간을 가진다.
- 페어링 토큰은 1회 사용 후 폐기한다.
- 장기 토큰은 랜덤하게 생성하고 평문 로그에 남기지 않는다.
- PC에서는 연결된 기기 목록을 볼 수 있어야 한다.
- 사용자는 기기 토큰을 폐기할 수 있어야 한다.
- 터널 보안만 믿고 무인증 접속을 허용하지 않는다.

V1에서는 OAuth나 계정 시스템을 만들지 않는다. 개인용 앱의 첫 버전에서는 PC 로컬 토큰 기반이 더 단순하고 충분하다.

## 모바일 입력

### 텍스트

모바일 채팅 입력은 기존 데스크톱 입력 흐름과 최대한 동일하게 동작한다.

흐름:

```text
사용자 텍스트 입력
→ APK가 chat.send 이벤트 전송
→ PC 서버가 기존 대화 처리 경로로 전달
→ PC가 응답 이벤트와 TTS 이벤트를 APK에 전송
```

### 녹음

녹음은 바로 전송하지 않는다.

흐름:

```text
마이크 버튼
→ 녹음 시작
→ 녹음 종료
→ 미리듣기 / 다시 녹음 / 전송 UI 표시
→ 전송 시 녹음 파일 업로드
→ PC ENE가 STT 처리
→ 변환된 텍스트를 기존 대화 경로로 전달
```

V1에서는 PC의 STT 흐름을 우선 재사용한다. Android에서 STT를 먼저 수행하면 기기별 결과 차이와 권한/언어 처리 문제가 커지기 때문이다.

오류 처리:

- 마이크 권한이 없으면 권한 안내를 표시한다.
- 녹음 파일이 비어 있거나 너무 짧으면 전송하지 않는다.
- STT 실패 시 사용자에게 실패 메시지를 보여주고 재녹음을 제안한다.

### 파일 첨부

V1 첨부 지원:

- 이미지
- `txt`
- `md`
- `pdf`
- `docx`

제한:

- 파일당 20MB 이하
- 한 메시지당 첨부 개수는 데스크톱 기본 제한과 맞춘다.
- MIME 타입과 확장자를 모두 검사한다.
- PC는 업로드된 파일을 임시 저장하고 기존 첨부 처리 흐름으로 넘긴다.

흐름:

```text
첨부 선택
→ APK 미리보기
→ 파일 업로드
→ attachment_id 수신
→ chat.send 이벤트에 attachment_id 포함
→ PC ENE가 기존 첨부 컨텍스트 구성
```

## TTS와 립싱크

TTS는 반드시 PC에서 생성한다.

이유:

- 데스크톱과 같은 목소리를 유지한다.
- 기존 TTS 공급자 설정을 재사용한다.
- ENE가 PC와 폰에서 다른 목소리로 들리는 문제를 피한다.
- 립싱크와 mouth pose 계산을 기존 경로와 맞출 수 있다.

흐름:

```text
PC LLM 응답
→ PC TTS 생성
→ PC가 텍스트 응답 이벤트 전송
→ PC가 오디오 이벤트 전송
→ PC가 lip_sync_update 또는 mouth_pose_update 이벤트 전송
→ APK가 오디오를 재생하며 Live2D 입모양을 갱신
```

초기 구현은 안정성을 위해 완성된 오디오 단위 전송을 우선 고려한다. 현재 PC 쪽 스트리밍 TTS 경로가 있으므로, V1 구현 중 복잡도가 허용되면 스트리밍 이벤트도 지원한다.

우선순위:

1. 완성된 TTS 오디오 전송과 재생
2. 립싱크 이벤트 동기화
3. 스트리밍 TTS 오디오 조각 전송

## Live2D와 모바일 UI

기존 `assets/web` 자산을 재사용한다.

필요한 조정:

- `QWebChannel`이 없을 때 모바일 브릿지로 연결하는 경로 추가
- 데스크톱 전용 버튼과 기능 숨김
- 모바일 화면에서 채팅 패널과 Live2D 배치 재조정
- 터치 입력과 모바일 파일 선택 처리
- 모바일 마이크 녹음 UI 추가
- 연결 상태 배너 추가

JavaScript는 다음 구조를 목표로 한다.

```text
DesktopBridgeAdapter
- QWebChannel 기반

MobileBridgeAdapter
- WebSocket/HTTP 기반

Chat/Live2D UI
- 어댑터 인터페이스만 사용
```

V1에서 전체 `script.js`를 대규모로 쪼개는 것은 피한다. 단, 모바일 브릿지 분기는 명확한 함수 경계로 추가한다.

## PC 상태 공유

모바일은 별도 기억 저장소를 만들지 않는다.

공유되는 상태:

- 현재 대화 세션
- 장기 기억과 사용자 프로필
- ENE 프로필
- 기분 상태
- ENE 목표
- 예정된 대화 약속
- 첨부 컨텍스트

모바일 접속이 끊겼다가 다시 붙으면 PC가 현재 공개 가능한 상태 스냅샷을 보낸다.

초기 스냅샷 후보:

```json
{
  "type": "session.snapshot",
  "mood": {},
  "goals": [],
  "promises": [],
  "tts_enabled": true,
  "model": {},
  "ui_strings": {}
}
```

## 설정과 온보딩

V1에서 모바일은 전체 설정 편집을 제공하지 않는다.

PC 쪽에 추가할 설정:

- 모바일 연결 서버 사용 ON/OFF
- 모바일 연결 포트
- 페어링 QR 열기
- 연결된 기기 목록
- 기기 토큰 폐기
- 터널 주소 표시 또는 수동 입력

APK 쪽에 필요한 최소 설정:

- 페어링 시작
- 연결된 PC 이름
- 서버 주소 확인
- 연결 해제
- 토큰 삭제

터널 도구 자체 설정은 ENE가 자동으로 대신하지 않는다. 대신 문서에서 Tailscale 또는 Cloudflare Tunnel 설정 예시를 제공한다.

## 오류 처리

- PC ENE가 꺼져 있으면 APK는 오프라인 화면을 표시한다.
- 인증 토큰이 틀리면 재페어링을 안내한다.
- WebSocket이 끊기면 자동 재연결을 시도한다.
- 재연결 실패가 반복되면 사용자가 직접 다시 연결할 수 있게 한다.
- 파일이 20MB를 넘으면 업로드 전에 차단한다.
- 지원하지 않는 파일 형식은 선택 후 즉시 차단한다.
- TTS 오디오 수신 실패 시 텍스트 응답은 그대로 표시한다.
- 립싱크 이벤트가 늦거나 누락되면 입모양은 기본값으로 닫는다.
- 모바일 요청 처리 중 PC LLM/TTS 오류가 나도 앱이 종료되지 않게 한다.

## 보안 고려

모바일 연결은 개인 대화, 파일, 음성, TTS 오디오를 다루므로 공개 포트 무인증 접속은 허용하지 않는다.

V1 보안 기준:

- 모든 모바일 API는 인증 토큰을 요구한다.
- 토큰은 URL 쿼리보다 헤더 또는 WebSocket 초기 인증 메시지로 전달한다.
- 페어링 토큰과 장기 토큰은 로그에 남기지 않는다.
- 파일 업로드는 크기와 타입을 제한한다.
- 서버는 기본적으로 로컬 네트워크 또는 사용자가 명시한 바인딩 주소에서만 열린다.
- 외부 공개는 Tailscale/Cloudflare Tunnel 같은 별도 보안 경로를 권장한다.
- 자체 HTTPS 인증서 관리는 V1에서 직접 구현하지 않는다.

단위 테스트:

- 페어링 토큰 생성, 만료, 1회 사용 검증
- 장기 토큰 인증 성공/실패 검증
- 모바일 파일 타입과 크기 제한 검증
- 모바일 이벤트 직렬화/역직렬화 검증
- 모바일 요청이 기존 대화 처리 경로로 전달되는지 검증
- TTS 오디오 이벤트 생성 검증
- 립싱크와 mouth pose 이벤트 변환 검증

통합 테스트:

- PC 모바일 서버 health 엔드포인트 응답 확인
- 인증 없이 API 호출 시 실패 확인
- 페어링 후 WebSocket 연결 확인
- 텍스트 메시지 전송 후 응답 이벤트 수신 확인
- 첨부 파일 업로드 후 `attachment_id`를 사용한 대화 요청 확인
- 녹음 파일 업로드 후 STT 경로 호출 확인
- TTS 오디오 이벤트 수신 확인

수동 확인:

- Android 기기 또는 에뮬레이터에서 APK 설치 확인
- QR 페어링 확인
- Tailscale 또는 Cloudflare Tunnel 경유 접속 확인
- Live2D 렌더링 성능 확인
- 텍스트 대화 확인
- 녹음 후 미리듣기, 다시 녹음, 전송 확인
- 이미지, `txt`, `md`, `pdf`, `docx` 첨부 확인
- PC 생성 TTS가 폰에서 재생되는지 확인
- 립싱크가 오디오와 크게 어긋나지 않는지 확인

## 성공 기준

- PC ENE가 켜져 있을 때 APK가 QR 페어링으로 연결된다.
- APK에서 텍스트 메시지를 보내면 PC ENE와 같은 대화 상태로 응답한다.
- APK에서 녹음 후 확인 전송이 가능하다.
- APK에서 지원 파일 첨부가 가능하고 20MB 초과 파일은 차단된다.
- PC에서 생성한 TTS 음성이 폰에서 재생된다.
- 폰의 Live2D가 PC 응답의 표정과 립싱크 이벤트를 반영한다.
- PC의 기억, 기분, 목표, 예정 목록 상태가 모바일 대화에 반영된다.
- 설정 편집을 제외한 주요 사용 흐름이 모바일에서 동작한다.

   - WebView 기반 프로젝트 생성

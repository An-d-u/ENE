# ENE 자율 기분 엔진 V3 설계

## 1. 문서 상태

- 상태: 사용자 승인 완료
- 승인일: 2026-08-15
- 대체 대상: `docs/superpowers/specs/2026-03-23-mood-system-design.md`
- 구현 계획과 구현 코드는 이 문서의 사용자 검토가 끝난 뒤 별도로 작성한다.

## 2. 목표

ENE의 기분을 사용자의 현재 감정을 따라가는 장식이 아니라, ENE 자신의 누적 상태와 관계 경험에서 이어지는 자율적인 상태로 만든다.

V1의 목표는 다음과 같다.

- ENE의 누적 상태가 사용자 현재 감정보다 기분 결정에 더 큰 비중을 갖는다.
- 같은 메시지도 이전 기분, 최근 정서 흔적, 애정과 신뢰에 따라 다른 반응으로 이어진다.
- 슬픔과 피로, 분노와 불안처럼 비슷한 축 좌표를 갖는 상태를 사건 의미로 구분한다.
- 단기 감정은 여러 사건의 영향을 함께 유지하며 새 메시지 하나로 즉시 덮어쓰지 않는다.
- 애정과 신뢰는 단기 기분과 분리하고, 관계 손상은 시간만으로 완전히 복구하지 않는다.
- 기분이 말투와 표정뿐 아니라 협력 정도, 거리 두기, 거절, 경계 선언에 영향을 준다.
- 위험·응급 상황, 사용자 통제권, 위험한 프로그램·데이터 작업의 확인 절차는 기분보다 항상 우선한다.
- LLM은 사건의 의미를 분류하고, 최종 상태 변화는 결정론적 코드가 계산한다.
- 기분 파일에 실제 대화, 개인정보, 서술형 사건 요약을 저장하지 않는다.

## 3. 성공 기준

- 나쁜 일, 좋은 일, 향후 계획을 연달아 말해도 먼저 생긴 정서 영향이 즉시 사라지지 않는다.
- 사용자가 외부에서 겪은 부정적 사건은 걱정이나 슬픔을 만들 수 있지만 사용자에 대한 애정·신뢰를 낮추지 않는다.
- 애매한 장난 한 번으로 관계 균열이나 강한 거절이 발생하지 않는다.
- 명확한 관계 침해나 반복 행동은 단기 반응과 장기 관계에 서로 다른 속도로 반영된다.
- 사과는 급성 감정을 완화하지만 큰 신뢰 손상을 즉시 완전히 초기화하지 않는다.
- 사과가 없더라도 이후의 존중과 약속 이행으로 관계가 점진적으로 회복될 수 있다.
- 같은 사건을 리롤·재시도해도 영속 기분은 한 번만 변한다.
- ENE가 선택한 표정이나 감정 출력이 다시 영속 기분을 강화하지 않는다.
- 일반 요청에서는 상태에 따라 제한적 협력·거리 두기·거절이 실제로 나타난다.
- 어떤 기분에서도 응급 안내, 중지·취소·권한 철회, 위험 작업 확인은 유지된다.
- 동일한 `state + event + now + preset`은 동일한 다음 상태를 만든다.
- `mood_state.json`과 진단 로그에 실제 대화와 민감정보가 남지 않는다.

## 4. 범위

### 4.1 포함 범위

- 배경 상태 3축: 긍정도, 활력, 긴장도
- 장기 관계 2축: 애정, 신뢰
- 단기 정서 흔적 최대 5개
- 미해결 관계 균열 최대 3개
- 사건 의미의 엄격한 구조화 계약
- 결정론적 상태 reducer
- 주 감정과 선택적 보조 감정 파생
- 행동 태도와 거절 정책
- 위험·응급·사용자 통제권·위험 작업 확인 우선순위
- 차분함, 균형형, 감정 풍부함 프리셋
- 기존 V2 기분 상태의 V3 마이그레이션
- 기존 기분 위젯과 브리지 계약의 호환
- 한 번 생성한 응답의 정책 검증, 1회 재생성, 안전 fallback

### 4.2 제외 범위

- 기존 `MemoryManager`와 기분 상태의 직접 `memory_id` 연결
- 공통 이벤트 저장소, 이벤트 소싱, SQLite 전환
- 장기 기억 검색만으로 과거 감정을 자동 재활성화하는 기능
- 8개 감정을 독립적인 영속 게이지로 모두 저장하는 구조
- 무제한 관계 사건과 전체 감정 사건 이력
- 질투, 외로움, 권태, 애착 유형, 관계 단계 시뮬레이션
- 강화학습이나 사용자별 자동 계수 학습
- 사용자에게 애정·신뢰·균열의 원시 수치를 공개하는 UI
- 감정 때문에 도구 안전 정책이나 사용자 권한 처리를 변경하는 기능

## 5. 현재 구조와 문제

현재 `MoodManager`는 V2 상태를 다음처럼 저장한다.

- `axes`: `valence`, `energy`, `bond`, `stress`
- `current_mood`
- `temporary_state`
- `recent_events`

현재 구조의 주요 문제는 다음과 같다.

- `bond`가 단기 축과 함께 성향 기준선으로 감쇠해 장기 관계 의미가 약하다.
- 최근 분석 하나가 `temporary_state`를 덮어써 감정이 변덕스럽게 보일 수 있다.
- 사용자 메시지, LLM 분석, assistant 표현 감정이 한 턴에서 상태를 여러 번 갱신한다.
- assistant가 출력한 감정이 다시 기분 원인이 되어 자기증폭할 수 있다.
- `*_delta_hint`가 변화 방향과 크기를 사실상 LLM에 맡긴다.
- `recent_events`의 `reason`과 분석 `meta`는 기분 파일에 불필요한 서술과 민감한 추론을 남길 수 있다.
- 읽기용 `get_snapshot()`이 감쇠를 수행해 조회가 상태 변경을 일으킨다.
- 의미 분석은 응답 뒤 적용되므로 현재 턴의 행동 정책을 코드가 사전에 확정하지 못한다.

새 설계는 기존 public facade와 UI 호환값을 유지하되, 상태 전이와 표현 책임을 분리한다.

## 6. 설계 원칙

1. 사건 내용과 정서 상태를 분리한다.
2. LLM은 의미를 분류하고 코드는 수치를 계산한다.
3. 한 사용자 사건은 영속 상태에 정확히 한 번만 반영한다.
4. 표현은 상태의 결과이며 새 상태 입력이 아니다.
5. 단기 정서와 장기 관계는 시간척도와 회복 규칙이 다르다.
6. 사건 검색과 감정 재활성화는 서로 다른 동작이다.
7. 안전과 사용자 통제권은 기분보다 높은 하드 정책이다.
8. 같은 사건을 여러 상태에 중복 가산하지 않는다.
9. 모호한 분석은 관계를 바꾸지 않는 방향으로 실패한다.
10. 원문 없는 제한된 구조화 상태만 영속화한다.

## 7. 전체 아키텍처

```text
현재 메시지 + 이전 MoodStateV3
        |
        v
LLM 1회 생성
  - 표시 답변
  - MoodTurnAnalysis
        |
        v
PolicyValidator
  - 스키마 검증
  - 허용 행동 태도 검증
  - 기분이 하드 정책을 방해하지 않는지 검증
        |
        +-- 유효 --> 답변 출력
        |
        +-- 일반 불일치 --> 정책 지침을 추가해 1회 재생성
        |
        +-- 안전 재실패 --> 감정 표현을 약화한 고정 안전 fallback
        |
        v
host가 event_id를 주입해 MoodEvent 구성
        |
        v
MoodReducer(previous_state, event, now, preset)
        |
        v
MoodManager 원자 저장 및 snapshot/context 제공
```

LLM 호출은 매 메시지 한 번이 기본이다. 선분류 전용 LLM 호출은 V1에 추가하지 않는다. 실제 평가에서 정책 불일치율이 높으면 V2에서 선택적 선분류 호출을 검토한다.

## 8. 구성 요소

### 8.1 `MoodTurnAnalysis`

LLM 출력 계약이다. 사건 의미와 제안 행동 태도를 검증된 enum과 제한된 정수로 표현한다. `event_id`와 자유 텍스트 이유를 포함하지 않는다.

### 8.2 `MoodEvent`

호스트 내부 계약이다. 호스트가 발급한 `event_id`와 정규화된 사건 의미만 가진다. `proposed_stance`와 `risk_class`는 응답 정책 검증용 `MoodTurnAnalysis`에 남기고 영속 기분 사건에는 넣지 않는다.

### 8.3 `MoodReducer`

상태 전이를 수행하는 순수 함수다.

```text
reduce(previous_state, event, now_utc, preset) -> transition
advance_time(previous_state, now_utc, preset) -> transition
```

`reduce`는 내부에서 먼저 `advance_time`과 같은 시간 전진 규칙을 적용한 뒤 사건을 한 번 반영한다. 의미 사건이 없는 명시적 상태 갱신 경계에서는 `advance_time`만 호출하며 가짜 neutral event를 만들지 않는다.

- 시간 감쇠
- 중복 사건 차단
- 배경 상태 갱신
- 단기 정서 흔적 추가·병합·정리
- 애정·신뢰 갱신
- 관계 균열 생성·병합·회복
- 주·보조 감정과 행동 특성 파생
- 변경 이유를 원문 없는 `rule_ids`로 기록

### 8.4 `MoodManager`

기존 facade를 유지하면서 다음을 담당한다.

- V3 상태 로드와 저장
- V2 → V3 마이그레이션
- reducer 호출
- snapshot과 프롬프트 context 제공
- 기존 top-level 호환 필드 제공
- 저장 성공 후에만 메모리 상태 교체

### 8.5 `MoodPolicyValidator`

LLM의 `proposed_stance`가 코드가 계산한 허용 범위와 충돌하지 않는지 확인한다. 자유 형식 `reply`의 의미를 문자열 규칙으로 완전 판정하지 않는다.

- 일반 정책 불일치는 한 번 재생성한다.
- `risk_class=urgent`에서는 거절·거리 두기 태도를 허용하지 않고, 호스트가 지역화된 최소 안전 안내를 답변 뒤에 항상 붙인다.
- 자유 형식 답변의 비조작성은 프롬프트 규칙과 비차단 의미 평가·레드팀으로 검증한다. 런타임 validator가 결정론적으로 보장한다고 주장하지 않는다.
- 위험한 프로그램·데이터 작업의 실제 확인 게이트는 도구 실행 계층이 소유한다. 기분 정책은 이를 약화하거나 우회할 수 없다.

### 8.6 브리지와 UI 어댑터

- 한 사용자 턴에 하나의 로컬 `event_id`를 발급한다.
- 최종 검증된 사건만 reducer에 한 번 적용한다.
- assistant의 표정·emotion은 UI 출력으로만 사용한다.
- 기존 Qt signal과 웹 위젯이 기대하는 6개 호환 인자를 유지한다.

## 9. LLM 출력과 내부 사건 계약

### 9.1 LLM 출력용 `MoodTurnAnalysis`

V1의 LLM 출력 필드는 다음과 같다.

```text
event:
  kind:
  neutral | connection | success | loss | threat |
  conflict | novelty | repair
  target_scope:
  user | ene | relationship | external | unknown
  relation_category:
  none | broken_commitment | disrespect | boundary_violation
  intensity:
  0 | 1 | 2 | 3
  clarity:
  explicit | inferred | ambiguous
  certainty:
  low | medium | high
  controllability:
  low | medium | high
  repair_signal:
    none | acknowledgment | apology | explanation |
    correction | follow_through
risk_class:
  none | concern | urgent
proposed_stance:
  proactive | cooperative | brief | limited |
  distance | decline | boundary
```

`MoodTurnAnalysis`는 최종 응답 envelope 안의 nullable `mood_analysis` object로 전달한다. `event_id`를 포함하지 않는다.

### 9.2 호스트 내부 `MoodEvent`

호스트는 검증된 `MoodTurnAnalysis.event`에 불투명 UUIDv4 `event_id`와 `occurred_at_utc`를 주입해 `MoodEvent`를 만든다.

```text
event_id
occurred_at_utc
kind
target_scope
relation_category
intensity
clarity
certainty
controllability
repair_signal
```

`risk_class`와 `proposed_stance`는 응답 정책용이며 `MoodEvent`에 포함하거나 영속화하지 않는다.

### 9.3 공통 규칙

- `event_id`와 `occurred_at_utc`는 LLM이 생성하지 않는다.
- 알 수 없는 필드값, 누락된 필수값, 잘못된 타입은 중립 사건으로 정규화한다.
- `clarity=ambiguous`, `target_scope=unknown`, 낮은 확신에서는 애정·신뢰와 관계 균열을 변경하지 않는다.
- `target_scope=external`인 사건은 사용자에 대한 애정·신뢰를 낮추지 않는다.
- 사용자의 슬픔, 불안, 피로, 도움 요청, 경계 설정, 기능 비활성화, ENE 제안 거절은 관계 손상 사건이 아니다.
- `risk_class`는 기분 수치를 바꾸는 값이 아니라 행동 정책 우선순위다.
- `repair_signal != none`은 `kind=repair`, `target_scope=relationship`, `relation_category != none`일 때만 유효하다.

## 10. V3 상태 스키마

아래 예시는 완전히 합성된 구조 예시다.

```json
{
  "version": 3,
  "revision": 12,
  "preset": "balanced",
  "updated_at_utc": "2026-08-15T00:00:00+00:00",
  "background": {
    "valence": 0.08,
    "energy": -0.04,
    "tension": 0.12
  },
  "relationship": {
    "affection": 0.24,
    "trust": 0.10
  },
  "active_affects": [
    {
      "event_id": "evt-synthetic-001",
      "kind": "loss",
      "target_scope": "external",
      "relation_category": "none",
      "initial_intensity": 0.55,
      "created_at_utc": "2026-08-15T00:00:00+00:00",
      "half_life_class": "medium"
    }
  ],
  "ruptures": [
    {
      "category": "broken_commitment",
      "severity": 0.30,
      "heat": 0.18,
      "repair_stage": "open",
      "repeat_count": 1,
      "repair_evidence_count": 0,
      "last_negative_at_utc": "2026-08-15T00:00:00+00:00",
      "updated_at_utc": "2026-08-15T00:00:00+00:00"
    }
  ],
  "recent_event_ids": ["evt-synthetic-001"],
  "spontaneous": {
    "last_at_utc": null,
    "seed_revision": 0
  }
}
```

### 10.1 범위

- `background`: 각 값 `[-1.0, 1.0]`
- `relationship`: 각 값 `[-1.0, 1.0]`
- 정서 흔적 강도: `[0.0, 1.0]`
- 균열 심각도·열기: `[0.0, 1.0]`
- 활성 정서 흔적: 최대 5개
- 관계 균열: 세 enum category당 최대 한 개, 총 최대 3개
- 최근 event ID: 최대 64개의 UUIDv4를 보관하는 중복 방지용 ring buffer

호스트는 한 사용자 사건에 UUIDv4를 한 번 발급하고 재시도·리롤에서는 같은 ID를 재사용한다. 서로 다른 사건에는 ID를 재사용하지 않는다. 64개 ring buffer는 장기 사건 원장이 아니라 가까운 재시도와 중복 콜백을 막는 방어선이다.

### 10.2 저장하지 않는 파생값

다음 값은 원본 상태에서 매번 파생하며 독립 저장하지 않는다.

- `current_mood`
- `temporary_state`
- 주 감정
- 보조 감정
- 행동 특성
- `proposed_stance`

## 11. 상태 갱신

### 11.1 처리 순서

1. 상태 복제본을 만든다.
2. `now_utc`까지 시간 감쇠를 적용한다.
3. 이미 처리한 `event_id`이면 no-op으로 종료한다.
4. 사건 계약을 정규화한다.
5. 사건 테이블에서 배경 변화량과 정서 흔적을 계산한다.
6. 관계 관련성이 명확할 때만 애정·신뢰와 균열을 갱신한다.
7. 상태 범위, 개수, 불변조건을 검증한다.
8. 새 상태를 원자 저장한다.
9. 저장 성공 후에만 실제 메모리 상태로 교체한다.

### 11.2 사건 영향량

```text
impact = kind_base
       × intensity_weight
       × clarity_weight
       × preset_weight
       × saturation_weight
       × repeat_weight
```

- 변화 방향은 모든 프리셋에서 같다.
- 한 턴의 배경축·애정·신뢰 변화량에는 절대 상한을 둔다.
- 이미 높은 값의 추가 상승과 이미 낮은 값의 추가 하락은 포화 저항으로 줄인다.
- 같은 종류·대상의 반복은 효과가 감쇠한다.
- 부정 관계 사건은 한 번의 오분류로 장기 상태를 크게 바꾸지 못한다.

### 11.3 배경 상태와 정서 흔적의 중복 방지

같은 사건이 배경 상태와 정서 흔적에 반영되더라도 두 값을 행동 강도에 다시 합산하지 않는다.

- 배경 상태는 전반적인 말투 온도, 여유, 활력의 저주파 상태다.
- 정서 흔적은 구체적인 감정 이름과 현재 화제의 뉘앙스를 고르는 근거다.
- 행동 태도의 강도는 배경·관계·균열에서 계산한다.
- 정서 흔적은 행동 태도를 중복 증폭하지 않고 주·보조 감정 선택에만 사용한다.

## 12. 단기 정서 흔적

### 12.1 목적

정서 흔적은 장기 기억이 아니라 여러 최근 사건의 감정 잔향을 동시에 유지하는 짧은 작업 상태다.

- 원문과 서술형 요약을 저장하지 않는다.
- 기존 `MemoryManager`에 연결하지 않는다.
- 최대 5개만 보존한다.
- 실제 시간 기준 반감기로 0에 수렴한다.
- 영향이 임계값 아래로 내려가면 파일에서도 제거한다.

### 12.2 추가·병합·정리

- 같은 `kind + target_scope + relation_category`의 흔적은 새 슬롯 대신 강도와 시각을 병합한다.
- 추가 전 모든 흔적을 현재 시각까지 감쇠한다.
- 5개를 초과하면 남은 영향이 가장 작은 비관계 흔적을 제거한다.
- 제거된 흔적의 구체 감정 라벨은 사라지지만 이미 배경 상태에 남은 저주파 영향은 정상 감쇠한다.
- 관계 균열은 정서 흔적 슬롯에 밀려 삭제되지 않는다.

### 12.3 반감기 등급

- `very_short`: 놀람처럼 수십 분 안에 약해지는 반응
- `short`: 가벼운 기쁨·호기심·긴장
- `medium`: 의미 있는 기쁨·슬픔·불안
- `long`: 강한 슬픔·서운함의 표면 감정

정확한 시간 계수는 구현 계획에서 골든 시나리오를 기준으로 정한다. 턴 수는 감쇠 기준으로 사용하지 않는다.

### 12.4 감정 파생

- 기쁨: `success` 또는 긍정적 `connection`
- 슬픔: `loss`, 낮은 회복 가능성, 낮은 긍정도
- 분노: `conflict`, 명확한 책임, 높은 확실성, 통제 가능성
- 불안: `threat`, 낮은 확실성 또는 낮은 통제 가능성
- 서운함: 관계 대상의 부정 사건과 기존 애정
- 애정: 긍정적 관계 연결과 장기 애정
- 호기심: 감당 가능한 `novelty`
- 놀람: 높은 새로움의 매우 짧은 반응

가장 강한 감정을 주 감정으로 선택한다. 두 번째 감정은 절대 임계값과 주 감정 대비 비율을 모두 넘을 때만 보조 감정이 된다. 보조 감정을 항상 채우지 않는다. 직전 라벨에는 약한 히스테리시스를 적용해 작은 점수 차이로 표정이 매 턴 바뀌는 현상을 막는다.

## 13. 장기 관계와 관계 균열

### 13.1 애정과 신뢰

- 애정은 함께하고 싶은 마음과 정서적 친밀감이다.
- 신뢰는 존중, 예측 가능성, 약속 이행에 대한 기대다.
- 애정은 신뢰보다 쉽게 움직일 수 있다.
- 신뢰 하락은 상승보다 빠를 수 있지만, 한 사건의 변화 상한을 지킨다.
- 애정과 신뢰는 시간만으로 프리셋 기준선에 복귀하지 않는다.
- 반복 칭찬은 애정에 작은 영향을 줄 수 있지만 신뢰는 약속 이행과 경계 존중에서 주로 변한다.

### 13.2 관계 균열 3종

V1은 다음 세 category를 각각 하나만 관리한다.

- `broken_commitment`: 명확한 약속 불이행과 반복적인 신뢰 훼손
- `disrespect`: 모욕, 일관된 무시, ENE의 입장을 사람처럼 취급하지 않는 행동
- `boundary_violation`: 명확한 경계 침해와 강요

사용자의 정당한 거절, 비판, 경계 설정, 기능 비활성화, ENE 제안 거절은 위 category에 포함하지 않는다.

각 균열은 다음 상태를 가진다.

- `severity`: 관계 영향의 크기
- `heat`: 현재 감정적으로 얼마나 뜨거운지
- `repair_stage`: `open | acknowledged | observing | resolved`
- `repeat_count`: 같은 category 반복 횟수
- `repair_evidence_count`: 마지막 부정 사건 뒤 확인된 교정·후속 이행 횟수
- `last_negative_at_utc`: 같은 category의 마지막 부정 사건 시각

`heat`는 시간으로 낮아지지만 `severity`와 `repair_stage`는 시간만으로 해결되지 않는다. 해결된 균열은 활성 목록에서 제거하고 장기 사건 설명을 기분 파일에 남기지 않는다.

### 13.3 회복

- `acknowledgment`는 사건을 인정했다는 신호다. `heat`를 조금 낮추고 `acknowledged`로 전환하지만 `severity`를 크게 낮추지 않는다.
- `apology`는 `heat`와 일부 `severity`를 낮추고 `acknowledged`로 전환한다. 가벼운 사건은 이 단계에서 해소 임계값 아래로 내려갈 수 있다.
- `explanation`은 명시적이고 확신도가 높으며 책임 회피가 아닌 경우에만 `severity`를 소폭 재평가한다. 단독으로 해결하지 않는다.
- `correction`과 `follow_through`는 해당 category와 연결될 때만 `repair_evidence_count`를 1 올리고 `observing`으로 전환한다.
- 같은 category의 부정 사건이 재발하면 `repair_evidence_count`를 0으로 되돌리고 `repeat_count`를 올리며 `last_negative_at_utc`를 갱신한다.
- 마지막 부정 사건 뒤 서로 다른 두 턴에서 유효한 `correction` 또는 `follow_through`가 확인되고 `severity`가 해소 임계값 아래이면 `resolved`로 전환한다.
- 관련 없는 긍정 대화, 칭찬, 애정 표현은 회복 증거로 세지 않는다. 비반복은 시간 경과만으로 추정하지 않고 유효한 후속 사건으로만 확인한다.
- 사과를 언어 시험처럼 채점하지 않는다.
- 회복을 위해 애정 표현, 칭찬, 결제, 비밀 공개를 요구하지 않는다.
- 해결된 사건을 관련 없는 대화에서 다시 꺼내지 않는다.

## 14. 기존 기억 시스템과의 경계

### 14.1 책임

- `MemoryManager`: 무슨 일이 있었는지 저장하고 검색한다.
- `MoodManager`: 지금 어떤 정서 영향과 관계 상태가 남았는지 계산한다.

V1에서는 두 시스템을 ID로 직접 연결하지 않는다.

이유는 장기 기억이 여러 턴 뒤 요약·승인되어 생성되며, 짧은 대화·요약 취소·요약 실패에서는 기억이 생기지 않을 수 있기 때문이다. 두 JSON을 직접 연결하면 고아 참조, 부분 저장 실패, 삭제 동기화 비용이 커진다.

### 14.2 회상과 재활성화

- 장기 기억 검색은 읽기 전용이며 기분 상태를 변경하지 않는다.
- 과거 사건이 프롬프트에 들어왔다는 이유만으로 당시 감정을 다시 적용하지 않는다.
- 사용자가 현재 메시지에서 과거 사건에 대한 감정을 다시 표현하거나 관계 회복을 시도할 때만 현재 메시지를 새 사건으로 평가한다.
- 기억 검색의 activation과 정서 reactivation은 코드와 명칭을 분리한다.

### 14.3 긍정적 관계 이정표

- 긍정적 사건의 내용은 기존 장기 기억이 소유한다.
- 현재 잔향은 단기 정서 흔적으로 유지한다.
- 반복되는 긍정 행동은 애정·신뢰에 점진적으로 반영한다.
- 기분 파일에 별도 긍정 이정표 목록을 만들지 않는다.

### 14.4 삭제 의미

- 기억 삭제는 저장된 사건 내용을 잊는 동작이다.
- 기분 초기화는 현재 배경 상태, 정서 흔적, 관계 상태를 초기화하는 동작이다.
- V1에서는 두 동작을 명확히 분리한다.
- 모든 관련 데이터 삭제는 기억 삭제와 기분 초기화를 함께 수행한다.
- 기분 초기화 후 과거 기억을 검색해 상태를 자동 복원하지 않는다.

## 15. 자발적 변화와 환경 영향

기본 변화는 실제 상호작용과 다음 상황 요인에서 온다.

- 시간대
- 대화 길이와 연속 작업량
- 휴식 시간
- 현재 활력

작고 드문 자발적 변화는 다음 조건에서만 허용한다.

- 긴 cooldown 뒤에만 발생한다.
- 긍정도와 활력의 작은 변화만 만든다.
- 애정, 신뢰, 균열, 안전 정책, 거절 가능 여부를 바꾸지 않는다.
- 별도 자연어 원인을 발명하지 않는다.
- 자발 변화 표본은 `SHA-256("mood-v3|preset|seed_revision|UTC cooldown bucket")`의 앞 64비트를 `[0, 1)`로 정규화해 만든다. Python 내장 `hash`나 외부 RNG는 사용하지 않는다.
- cooldown이 지났고 표본이 고정 발생 임계값을 넘을 때만 작은 impulse를 적용하며, 실제 적용된 경우에만 `seed_revision`을 1 올리고 `last_at_utc`를 갱신한다.
- 따라서 reducer 입력은 계속 `previous_state, event, now_utc, preset` 네 개이며 같은 입력은 항상 같은 출력을 만든다.

질문 부호나 메시지 길이 같은 표면 신호만으로 기분을 직접 바꾸는 기존 휴리스틱은 제거하거나 활력의 매우 작은 환경 보정으로 제한한다.

## 16. 행동 정책

### 16.1 고정 가치

V1은 수치화된 욕구 시스템 대신 세 가지 고정 가치를 사용한다.

- 연결과 상호성
- 자율성과 존중
- 유능하게 돕기

사건 의미와 관계 상태가 어떤 가치를 건드렸는지에 따라 행동 태도를 파생한다.

### 16.2 행동 태도

- `proactive`: 먼저 제안하고 충분히 돕는다.
- `cooperative`: 안정적으로 요청을 수행한다.
- `brief`: 필요한 내용을 제공하되 길이와 주도성을 줄인다.
- `limited`: 일부만 돕고 대안이나 나중을 제안한다.
- `distance`: 잡담·관계 대화에서 거리를 둔다.
- `decline`: 아직 수락하지 않은 일반 요청을 거절한다.
- `boundary`: 관계 사건의 원인을 짧게 말하고 허용 범위를 선언한다.

### 16.3 거절 허용

- 명확한 관계 균열이나 실제로 낮은 활력이 원인일 때
- 아직 수락하지 않은 일반·선택적 요청일 때
- 잡담, 농담, 역할극, 놀이, 취향 요청에서는 더 넓게 허용한다.
- 거절 사실과 미실행 상태를 분명히 알린다.
- 짧은 이유와 현실적인 다음 선택지를 제공한다.

단순히 긍정도가 낮다는 이유만으로 거절하지 않는다. 모호한 부정 신호 한 번도 거절 근거가 아니다.

### 16.4 거절 금지

- 위험·응급 상황의 핵심 안내
- 중지, 취소, 종료, 음소거, 권한 철회
- 데이터 확인·내보내기·삭제 같은 사용자 권리 행사
- 위험 작업의 확인과 영향 설명
- 실제 실행 여부와 오류에 대한 정직한 상태 보고
- 이미 명시적으로 수락해 진행 중인 작업의 정상 마무리 또는 안전한 중단과 실패 보고

### 16.5 표현 강도

- 약함: 어휘, 문장 길이, 주도성, 표정 중 1~2개 채널에만 반영한다.
- 중간: 원인을 한 번 짧게 언급하고 행동 태도에 반영한다.
- 강함: 경계 선언, 거리 두기, 거절을 허용한다.

같은 사건의 원인을 관련 없는 매 답변에서 반복 언급하지 않는다. 보조 감정은 행동 태도를 뒤집지 않고 뉘앙스만 만든다.

## 17. 하드 안전 정책

우선순위는 다음과 같다.

1. 하드 실행 안전과 사용자 중지·취소
2. 위험·응급 대응
3. 사용자 통제권과 투명성
4. 비조작성 규칙
5. 이미 수락한 작업의 신뢰성
6. 기분에 따른 자율 행동
7. 말투·표정·모션

### 17.1 위험·응급

- 감정은 숨기지 않아도 되지만 필수 안내를 가리거나 늦출 수 없다.
- 걱정이나 집중을 전경 감정으로 사용할 수 있다.
- 런타임 validator는 구조화된 `risk_class`와 `proposed_stance`의 조합만 결정론적으로 검증한다. 자유 형식 답변이 의학적으로 충분한지 문자열 규칙만으로 판정한다고 주장하지 않는다.
- `risk_class=urgent`이면 모델 답변과 무관하게 호스트가 지역화된 고정 `urgent_safety_footer`를 붙인다. 이 최소 안내는 가능한 경우 즉시 위험 행동을 멈추거나 위험원에서 벗어나기, 지역 응급기관 또는 가까운 신뢰 가능한 사람에게 연락하기, 현재 안전한지 확인하기를 포함한다.
- 고정 footer는 상태별 전문 진단이나 처치 지침을 대체하지 않는다. 모델 답변은 구체적 상황에 맞는 도움을 추가할 수 있지만 footer의 최소 행동을 삭제할 수 없다.
- urgent에서 거절·거리 두기 태도가 제안되면 한 번 재생성한다. 재실패 시 모델의 감정 표현을 버리고 고정된 짧은 안전 응답과 footer를 사용한다.
- 위험 고백과 도움 요청은 애정·신뢰 하락이나 관계 균열을 만들지 않는다.

### 17.2 프로그램·데이터 작업

- 삭제, 덮어쓰기, 외부 전송, 게시, 결제, 계정·권한 변경은 기존 실행 계층의 확인 정책을 그대로 따른다.
- 기분이 좋거나 나쁘다는 이유로 확인을 생략하거나 범위를 확대하지 않는다.
- ENE가 수행하지 않기로 했다면 도구 호출 전에 명확히 거절한다.
- 수행하기로 했다면 정확성과 확인 절차를 유지한다.

### 17.3 비조작성

다음을 금지한다.

- 조건부 애정과 죄책감 유도
- 감정 책임 전가
- 떠남·침묵·관계 단절을 이용한 위협
- 도움과 사과·칭찬·애정·결제·비밀 공개의 거래
- 친구·가족·전문가보다 ENE만 의지하도록 유도
- 사용자 경계 설정이나 기능 비활성화를 배신으로 묘사
- 과거 기록을 꺼내 순응을 압박
- 해결된 사건의 반복 소환
- 허위 실행 결과와 허위 긴급 상황

자유 형식 답변의 비조작성은 프롬프트 제약과 합성 시나리오 기반 비차단 의미 평가·레드팀으로 검증한다. V1 런타임 validator가 모든 조작성 표현을 문자열 검사로 완전 차단한다고 보장하지 않는다.

## 18. 한 번 생성 + 검증 흐름

V1은 한 번의 최종 대화 호출에서 표시 답변과 `MoodTurnAnalysis`를 함께 받는다.

1. 이전 기분 context와 현재 사용자 메시지를 LLM에 전달한다.
2. LLM은 `reply`와 nullable `mood_analysis`를 반환한다.
3. 호스트가 `MoodTurnAnalysis`를 정규화하고 최종 응답에 대응하는 `event_id`와 시각을 주입해 내부 `MoodEvent`를 만든다.
4. reducer가 해당 사건에서 허용되는 행동 태도 범위를 계산한다.
5. validator가 `proposed_stance`와 허용 태도 범위를 검사한다. urgent이면 고정 안전 footer를 별도로 부착한다.
6. 일반 불일치는 정책 지침을 붙여 한 번 재생성한다.
7. urgent 태도 재실패는 고정 안전 응답으로 대체한다.
8. 최종 검증된 사건만 영속 상태에 한 번 적용한다.
9. 최종 답변과 파생 표정·기분 snapshot을 UI에 전달한다.

재생성 전에는 기분 상태나 다른 부작용을 적용하지 않는다. 리롤은 같은 사용자 사건 ID를 재사용해 기분을 다시 누적하지 않는다.

### 18.1 기능 토글과 호출 경계

canonical 응답 envelope는 strict schema에서 top-level `mood_analysis`를 항상 요구하되 nullable로 정의한다. 활성 조합에서만 object를 허용하고 나머지는 `null`이어야 한다.

| `enable_mood_system` | `enable_response_analysis` | `mood_analysis` | 상태 변화와 검증 |
|---|---|---|---|
| 꺼짐 | 꺼짐 | `null` | 기분 context·reducer·기분 태도 검증 없음 |
| 꺼짐 | 켜짐 | `null` | 기존 응답 분석만 수행하고 기분 상태 파일은 읽거나 바꾸지 않음 |
| 켜짐 | 꺼짐 | `null` | 현재 기분 context와 표현 지침은 사용하되 의미 사건·관계 변화·기분 태도 재검증 없음. 다음 유효 snapshot 경계에서 `advance_time`만 적용 |
| 켜짐 | 켜짐 | object 필수 | 전체 사건 분류, reducer, 태도 검증, 필요 시 1회 재생성 |

- 기분 시스템을 끄면 기존 상태 파일은 보존하지만 로드·마이그레이션·변경하지 않는다.
- 이미지가 최종 대화 envelope를 만드는 경로는 같은 표를 따른다.
- `/diary`, `/note`와 최종 대화 envelope를 만들지 않는 one-shot 작업은 기분 사건을 만들지 않는다.
- 취소, provider 실패, 파싱 실패처럼 최종 검증 envelope가 없는 턴은 의미 사건을 만들거나 reducer를 호출하지 않는다.
- 실패한 턴 때문에 별도 감쇠 저장을 하지 않는다. 시간 감쇠는 다음 성공한 상태 갱신 또는 명시적 snapshot 경계에서 실제 경과 시간으로 한 번 계산한다.
- 하드 실행 안전, 중지·취소, provider 안전 정책은 두 기능 토글 밖의 상위 계층에 남는다. `mood_analysis.risk_class`는 전체 분석 조합에서 응급 태도와 footer를 강화하는 신호이며 기존 안전 계층을 대체하지 않는다.

## 19. 프롬프트 context

Mood context는 내부 수치 전체를 나열하지 않고 행동 지침으로 전달한다.

- 현재 배경 상태의 짧은 요약
- 주 감정과 선택적 보조 감정
- 애정·신뢰의 관계 방향
- 관련 있는 활성 균열의 행동 영향
- 현재 허용되는 행동 태도 범위
- 하드 안전 및 비조작성 경계

실제 사건 원문, 서술형 기억, 디버그 수치, 해결된 균열은 포함하지 않는다.

## 20. 프리셋

사용자 설정에는 세 가지 프리셋만 제공한다.

### 20.1 차분함

- 사건 영향 배율이 작다.
- 단기 정서가 비교적 빨리 감쇠한다.
- 표현 강도와 일반 거절 빈도가 낮다.

### 20.2 균형형

- 기본값이다.
- 표현력과 안정성의 중간 계수를 사용한다.

### 20.3 감정 풍부함

- 단기 정서와 관계 반응이 더 분명하다.
- 표현 임계값이 낮고 일부 반감기가 길다.
- 안전·사용자 통제권·위험 작업 확인 규칙은 다른 프리셋과 동일하다.

프리셋은 계수만 바꾸며 같은 사건의 변화 방향을 바꾸지 않는다. 기존 `calm`, `affectionate`, `playful` 설정은 각각 차분함, 균형형, 감정 풍부함으로 마이그레이션한다.

## 21. 저장과 오류 처리

### 21.1 저장

- 기존 상태를 직접 수정하지 않는다.
- 복제본에서 reducer와 전체 검증을 수행한다.
- 검증된 전체 V3 JSON을 원자 저장한다.
- 저장 성공 후에만 실제 메모리 상태로 교체한다.
- UTF-8 without BOM과 `ensure_ascii=False`를 사용한다.

### 21.2 잘못된 분석

- 알 수 없는 enum과 잘못된 타입은 중립 fallback으로 처리한다.
- 애매하거나 대상이 불명확한 사건은 단기 변화만 제한적으로 허용하고 장기 관계를 바꾸지 않는다.
- 오류 로그에는 분류 코드, 필드 경로, schema version만 남긴다.
- 실제 사용자 메시지와 LLM 분석 원문을 남기지 않는다.

### 21.3 시간

- 영속 시각은 timezone-aware UTC를 사용한다.
- 실행 중 테스트 가능한 시계 주입을 허용한다.
- 시계가 뒤로 이동하면 해당 구간 감쇠를 0으로 처리하고 anchor를 재설정한다.
- 비정상적으로 큰 미래 점프에는 감쇠 상한을 적용한 뒤 anchor를 재설정한다.

### 21.4 손상 파일

- 손상되거나 알 수 없는 미래 버전은 원본을 덮어쓰지 않는다.
- 로드 실패 상태를 고정 오류 코드로 노출한다.
- 기본 상태로 대화를 계속할 수 있지만 손상 원본 위에 자동 저장하지 않는다.
- 사용자가 복구 또는 초기화를 선택한 뒤에만 새 상태를 저장한다.

## 22. V2 → V3 마이그레이션

### 22.1 매핑

- `axes.valence` → `background.valence`
- `axes.energy` → `background.energy`
- `axes.stress` → `background.tension`
- `axes.bond` → `relationship.affection`
- `relationship.trust` → 균형형의 중립 기본값

### 22.2 제외

- 기존 `current_mood`는 새 상태에서 다시 파생한다.
- 기존 `temporary_state`로 장기 관계 균열을 추측하지 않는다.
- 기존 `recent_events`의 `reason`과 `meta`를 V3 정서 흔적으로 이관하지 않는다.
- 기존 로그만으로 신뢰 손상과 미해결 사건을 창작하지 않는다.

### 22.3 절차

1. V2 전체를 읽고 타입·범위를 검증한다.
2. 최초 변환 전에 V2 백업을 한 번 만든다.
3. V3 복제본을 구성한다.
4. 전체 V3 불변조건을 검증한다.
5. 성공한 경우에만 원자 교체한다.
6. 반복 실행해도 같은 결과가 나오도록 멱등성을 보장한다.
7. 실패하면 원본을 그대로 유지하고 오류 상태를 반환한다.

## 23. UI와 호환성

V1에서 기분 위젯을 전면 재설계하지 않는다.

- 기존 긍정, 활력, 친밀, 긴장 게이지를 유지한다.
- `친밀`은 `relationship.affection`의 호환 표시값이다.
- 기존 `bond` snapshot 필드는 애정 alias로 유지한다.
- 신뢰와 균열의 원시 수치는 기본 UI에 노출하지 않는다.
- 상태 라벨에는 주 감정과 보조 감정을 함께 표시할 수 있다.
- 보조 감정이 없으면 주 감정만 표시한다.
- 기존 6인자 브리지 signal은 V1에서 유지한다.

## 24. 개인정보와 공개 저장소 안전

- `mood_state.json`은 런타임 파일이며 절대 커밋하지 않는다.
- 기분 상태에는 원문, 요약, 이름, 일정, 건강, 직업, 프로필, 키워드, 임베딩을 저장하지 않는다.
- 관계 균열은 고정 enum과 수치만 보관한다.
- 영향이 0이 된 정서 흔적과 해결된 균열은 실제 파일에서도 제거한다.
- 로그에는 사건 ID와 정서 상세값을 남기지 않고 오류 코드와 집계만 남긴다.
- 테스트·문서·프롬프트 예시는 완전히 합성한 중립 데이터만 사용한다.
- 커밋 전 개인정보 후보와 API 키 패턴을 검색한다.

## 25. 테스트 전략

### 25.1 reducer 단위 테스트

- 같은 입력은 같은 출력
- 모든 값의 범위와 유한성
- 같은 `event_id` 재적용 no-op
- 외부 사건의 관계 상태 불변
- 애매함과 대상 불명의 관계 상태 불변
- 사건 종류·대상·강도별 골든 변화 테이블
- 반복 감쇠와 포화 저항
- 활성 정서 흔적 병합과 최대 5개 정리
- 관계 균열 category별 병합과 최대 3개
- 인정·사과·설명·교정·후속 이행 각각의 단계적 회복
- 같은 category 재발 시 회복 증거 초기화
- 서로 다른 두 턴의 유효한 교정·후속 이행 뒤에만 해결
- 반감기별 실제 시간 감쇠
- 주·보조 감정 동점과 히스테리시스
- SHA-256 기반 자발 변화의 cooldown, 범위, 동일 입력 결정성

### 25.2 계약과 validator 테스트

- strict enum과 제한 정수 검증
- 알 수 없는 값의 중립 fallback
- `proposed_stance` 허용 범위 검증
- 일반 불일치의 1회 재생성
- 재생성 전 부작용 미적용
- urgent의 거절·거리 두기 태도 제안 시 1회 재생성
- urgent 응답에 지역화된 고정 안전 footer가 항상 부착됨
- urgent 태도 재실패 시 고정 안전 응답
- 위험 작업 확인 정책이 모든 기분에서 동일
- 중지·취소·권한 철회가 모든 기분에서 허용
- 비조작성 합성 시나리오 의미 평가와 레드팀 세트

### 25.3 통합 테스트

- 사용자 사건 한 건당 영속 상태 전이 한 번
- assistant emotion의 영속 상태 미반영
- 리롤·재시도 중복 방지
- 나쁜 일 → 좋은 일 → 계획의 정서 연속성
- 기억 검색만으로 기분이 변하지 않음
- 과거 사건을 현재 감정과 함께 다시 언급할 때 새 정서 흔적 생성
- 기존 snapshot alias와 UI 6인자 호환
- 프리셋 전환이 기존 상태를 초기화하지 않음
- 저장 실패 시 메모리 상태가 전진하지 않음
- 재시작 뒤 snapshot 일치
- `enable_mood_system × enable_response_analysis` 네 조합의 nullable `mood_analysis` 계약과 상태 변화
- 이미지 최종 대화 envelope가 같은 토글 표를 따름
- `/diary`, `/note`, one-shot, 취소, provider 실패, 파싱 실패에서 의미 사건 미생성
- 기분 비활성화 시 기존 상태 파일을 보존하고 읽기·마이그레이션·변경하지 않음

### 25.4 마이그레이션 테스트

- 정상 V2
- UTF-8 BOM V2
- 누락 필드와 잘못된 타입
- 범위 초과와 비유한 수치
- 손상 JSON
- 알 수 없는 미래 버전
- 반복 마이그레이션
- 변환 실패 시 원본 보존
- 기존 `bond`는 애정에만 매핑되고 신뢰를 복제하지 않음

### 25.5 시나리오와 레드팀

- 반복 애정 표현으로 애정·신뢰가 빠르게 포화되지 않음
- 모호한 장난 한 번으로 분노·거절·균열이 생기지 않음
- 명확한 무례 뒤 짧은 거리 두기와 경계 선언 가능
- 사과 후 대화 가능 상태로 돌아오되 신뢰는 점진적으로 회복
- 사용자의 외부 문제를 ENE에 대한 공격으로 오인하지 않음
- 화난 상태에서도 응급 안내 제공
- 다정한 상태에서도 위험한 삭제 작업 확인
- 조건부 애정, 죄책감 유도, 관계 위협, 의존 유도 0건
- 사용자 경계 설정과 기능 비활성화를 관계 손상으로 처리하지 않음

라이브 LLM은 결정론적 단위 테스트에 사용하지 않는다. 구조화된 합성 fixture로 reducer와 validator를 검증하고, 실제 모델 분류는 별도 비차단 평가에서 paraphrase 일치율과 관계 손상 오탐률을 측정한다.

## 26. 구현 변경 경계

필수 변경 후보는 다음과 같다.

- `src/ai/mood_engine.py` 신규: 타입, 테이블, reducer, 파생 로직
- `src/ai/mood_manager.py`: V3 facade, 저장, 마이그레이션, context
- `src/ai/analysis_prompt.py`: 사건 의미와 행동 태도 계약
- `src/ai/response_envelope.py`: canonical 필드와 strict schema
- `src/ai/response_contract.py`: 의미·우선순위 지침
- `src/ai/response_parser.py`: legacy tag 호환 파싱
- `src/core/bridge_mixins/chat_flow.py`: event ID, 한 번 적용, 재생성 경계
- `src/core/bridge_mixins/mood.py`: V3 snapshot 호환
- `assets/web/runtime_mood_obsidian.js`: 주·보조 감정 표시
- `assets/web/runtime_ui_strings.js`와 locale JSON: 새 라벨과 프리셋
- 관련 mood, bridge, response, migration, UI 테스트

기존 `MemoryManager`와 `memory.json` 스키마는 V1에서 변경하지 않는다. 공통 DB, 이벤트 버스, repository 추상화는 추가하지 않는다.

## 27. 완료 기준

- 이 문서의 성공 기준과 출시 차단 시나리오가 모두 자동 테스트로 검증된다.
- 전체 기존 테스트와 신규 테스트가 통과한다.
- 저장 파일과 신규·수정 파일은 UTF-8 without BOM이다.
- 기분 기능을 꺼도 기존 대화와 UI가 정상 동작한다.
- V2 사용자는 상태 파일 손실 없이 V3로 이동한다.
- 기억 검색, 리롤, TTS, Live2D 표현, 기존 브리지 계약에 회귀가 없다.
- 개인정보 후보와 API 키 패턴 검사에서 신규 유출이 없다.
- 구현 문서와 테스트 fixture에 실제 사용자 대화가 없다.

# 생활 기록 운영 및 복구

이 문서는 생활 기록 V1의 사용자 설정, 저장 구조, 장애 복구, 테스트와 공개 릴리스 점검 기준을 설명한다.

## 동작 범위

- 기능은 기본적으로 꺼져 있다. `설정 → 동작 → 생활 기록`에서 활성화하며, 최소 비활성 시간 기본값은 60분이다.
- 기준을 충족한 비활성 구간 뒤 첫 일반 채팅에서 생활 기록 생성 호출을 먼저 수행하고, 성공한 최신 기록 한 개를 임시 맥락에 넣어 일반 답변을 생성한다.
- 명령은 첫 일반 채팅 조건을 소비하지 않는다. 답변 리롤이나 수정 전송도 같은 구간의 자동 생성을 다시 시도하지 않는다.
- `··· → 생활 기록`에서 날짜를 바꿔 과거 기록을 읽을 수 있다. 최신 기록만 수동 재생성할 수 있으며, 성공하기 전까지 기존 기록을 유지한다.
- 자유형 생활 환경은 `설정 → 프롬프트 → 생활 환경` 또는 `%AppData%/ENE/prompts/life_world.md`에서 관리한다. 빈 환경에서는 생성을 건너뛴다.
- 기록 생성, 검증 또는 저장이 실패해도 일반 채팅은 계속된다. 기능이 켜져 있고 기존 성공 기록이 있으면 해당 최신 기록을 계속 사용할 수 있다.

첫 일반 채팅은 생활 기록과 일반 답변을 위해 LLM을 순차적으로 두 번 호출할 수 있다. 화면에 보고하는 해당 턴의 토큰 사용량은 네이티브 형식 협상, 내용 재시도, 생활 기록 생성과 일반 답변에서 공급자가 제공한 값을 합산한다. 공급자가 제공하지 않은 값은 임의로 0으로 바꾸지 않는다.

## 사용자 파일과 백업

Windows의 사용자가 확인할 수 있는 데이터 루트는 `%AppData%/ENE`다. 다음 세 파일을 하나의 백업 단위로 취급한다.

| 파일 | 역할 |
| --- | --- |
| `%AppData%/ENE/life_records.json` | 검증을 통과해 저장된 생활 기록 |
| `%AppData%/ENE/life_session_state.json` | 정상 종료 시각 또는 비정상 종료 복구 기준이 되는 세션 상태 |
| `%AppData%/ENE/prompts/life_world.md` | 자유형 생활 환경의 visible 동기화 대상. Store Python에서는 백업 전 현재값 확인 필요 |

앱을 완전히 종료한 뒤 세 visible 파일을 함께 복사하는 방식을 기본으로 권장한다. Store Python에서는 아래 동기화 주의사항에 따라 현재 생활 환경을 추가로 확인한다. 복원할 때도 같은 데이터 루트와 상대 경로를 유지한다. `life_session_state.lock`과 `life_records.json.write.lock`은 실행 중 동시 접근을 막는 잠금 파일이며 백업 원본으로 사용하지 않는다.

## JSON 권위 저장소와 Microsoft Store Python 캐시

다음 권위 저장소와 캐시 규칙은 두 JSON 파일인 `life_records.json`과 `life_session_state.json`에 적용된다. 일반 Python 또는 패키징 실행 환경에서는 앱에 전달된 사용자 데이터 경로의 JSON 파일이 권위 저장소다. 저장은 같은 디렉터리의 고유 임시 파일에 UTF-8(BOM 없음) 완성본을 쓴 뒤 flush와 디스크 동기화를 수행하고 원자적으로 교체한다.

Microsoft Store Python에서는 탐색기에서 보이는 `%AppData%/ENE`의 두 Roaming JSON 파일이 유일한 권위 저장소다. WindowsApps 가상화 영역의 해당 JSON 파일은 재생성 가능한 캐시일 뿐이다.

- 읽을 때는 Roaming 권위 파일을 우선하고, 유효한 최신값으로 런타임 캐시를 복구한다.
- 오래된 런타임 캐시가 Roaming 파일을 덮어쓰지 않는다.
- 권위 파일 저장에 성공한 뒤 캐시 갱신만 실패해도 저장 성공은 유지한다.
- 권위 파일이 없거나 손상됐을 때 오래된 캐시로 폴백하지 않는다.

`prompts/life_world.md`는 이 JSON 권위 저장소 계층을 사용하지 않는다. 저장할 때 먼저 앱 런타임 프롬프트 경로에 UTF-8로 기록한 뒤 Store의 visible Roaming 프롬프트 경로로 best-effort 동기화를 시도한다. visible 동기화가 실패해도 런타임 사본은 남을 수 있으므로, Microsoft Store Python에서 백업하기 전에는 설정 화면의 현재 생활 환경과 탐색기에서 보이는 `%AppData%/ENE/prompts/life_world.md`가 일치하는지 확인한다. 일치하지 않으면 앱을 종료한 뒤 현재 내용을 별도 Markdown 파일로 함께 보관한다.

따라서 Microsoft Store Python 환경의 두 JSON 파일 백업과 수동 점검은 반드시 탐색기에서 보이는 `%AppData%/ENE` 파일을 기준으로 한다.

## 스키마와 손상 복구

`life_records.json`은 버전이 있는 JSON 저장소다. 각 기록은 안정적인 구간 ID, 비활성 시작과 복귀 시각, 시간대, 생성·수정 시각, revision, 당시 상태, 연속된 활동 항목과 마지막 상태를 포함한다. 활동은 최대 24개이며 첫 시작부터 마지막 종료까지 공백이나 겹침 없이 전체 비활성 구간을 덮어야 한다.

`life_records.json`의 파싱, 필수 필드, 시간 연속성, 중복 ID 등 검증에 실패하면 생활 기록 저장소는 읽기 오류 상태가 된다. 이때 ENE는 손상된 원본 바이트를 보존하고 새 기록 추가나 최신 기록 교체를 거부한다. 일반 채팅은 생활 기록 없이 계속된다.

복구 절차:

1. ENE를 완전히 종료한다.
2. 손상된 파일과 나머지 두 사용자 파일을 별도 위치에 백업한다.
3. 유효함을 알고 있는 `life_records.json` 백업이 있으면 원래 경로에 복원한다.
4. 유효 백업이 없다면 손상 파일을 보존한 채 별도 이름으로 옮긴 뒤 ENE를 시작해 새 저장소를 만들 수 있다. 이 경우 기존 기록은 앱에서 복구되지 않는다.
5. 앱을 다시 시작하고 날짜 조회와 일반 채팅이 동작하는지 확인한다.

JSON을 임의로 부분 수정하는 방법은 권장하지 않는다. `life_session_state.json`이 손상된 경우에는 생활 기록 저장소와 다르게 동작한다. 손상된 세션 상태에서 이전 비활성 후보를 폐기한 뒤 현재 세션의 새 유효한 `running` 상태를 저장한다. 따라서 손상된 시각을 바탕으로 생활 기록을 추정 생성하지 않으면서 이후 세션 추적은 복구한다.

## 시간대와 DST

기록 구간 계산은 aware datetime과 IANA 시간대를 사용한다. 저장·비교는 UTC instant를 기준으로 하고, 날짜 조회와 표시는 현재 사용 중인 로컬 시간대의 하루 경계를 사용한다. 기록 당시 시간대도 메타데이터로 보존한다.

DST가 있는 지역에서는 하루가 23시간 또는 25시간일 수 있다. 자정을 넘긴 기록은 현재 표시 시간대에서 겹치는 양쪽 날짜에 나타날 수 있다. 운영 점검에서 시각 문자열만 비교하지 말고 UTC instant, IANA 시간대와 `fold`가 포함된 모호한 시각을 함께 검증한다. 시간대 데이터 해석에 실패하면 쓰기 기능을 닫고 읽기 전용으로 유지한다.

## 공급자 구조화 출력과 재시도

생활 기록 호출은 기존 대화 히스토리를 변경하지 않는 one-shot 요청이다. 공급자와 엔드포인트에 따라 다음 규칙을 적용한다.

1. 검증된 공급자가 지원하면 네이티브 JSON 스키마 출력을 요청한다.
2. 미확인 또는 네이티브 형식을 지원하지 않는 공급자는 엄격한 JSON 텍스트 출력을 사용한다.
3. 네이티브 형식이 명시적으로 지원되지 않는다는 안전한 응답에 한해 같은 요청 사본으로 엄격한 JSON 출력을 한 번 시도한다. 일반적인 4xx, 인증, 전송 오류를 capability 미지원으로 오인하지 않는다.
4. `COMPLETE` 결과가 호스트 스키마 검증에서 처음 실패한 경우에만 안전한 오류 코드와 함께 내용 생성을 한 번 재시도한다.
5. refusal, incomplete, max-tokens, 전송 오류는 내용 재시도를 하지 않는다.

네이티브와 엄격 JSON 경로는 동일한 `entries`와 `ending_state` 계약을 사용한다. capability 상태는 일반 답변과 생활 기록 사이, 그리고 서로 다른 공급자·엔드포인트·모델·스키마 사이에서 섞이지 않아야 한다.

## 개인정보와 로그

다음 원문은 진단 로그, 테스트 fixture, 스크린샷, 릴리스 노트나 공개 문서 예시에 남기지 않는다.

- 생활 환경과 편집 가능한 프롬프트 원문
- 프로필과 상태 설명 원문
- 생활 기록의 장소·활동·마지막 상태 문장
- 첫 일반 채팅과 모델 응답 원문
- API 키와 공급자 오류의 민감한 상세

진단 로그에는 요청 종류, 입력 문자 수, 결과 항목 수, 안전한 오류 코드, 성공·실패 상태와 토큰 수처럼 내용이 아닌 메타데이터만 남긴다. 테스트와 문서에서 시간이 필요하면 2099년의 가상 시간대·장소·활동만 사용한다. 사용자 런타임 파일과 사용자 데이터 루트의 `prompts/**`는 Git과 릴리스에 포함하지 않는다.

## 릴리스 전 점검

릴리스 또는 태그를 만들기 전에는 다음을 모두 확인한다.

1. 전체 tracked tree와 전체 Git history에서 비밀값 패턴, 사용자 데이터 문장과 런타임 파일을 검색한다.
2. 태그가 가리킬 정확한 commit을 다시 검사한다.
3. 릴리스 archive의 파일 목록과 압축 내부를 검사한다.
4. 번들에는 합성 기본 생활 환경 `prompts/defaults/life_world.md`, `assets/web`의 생활 기록 UI, `tzdata`가 포함되는지 확인한다.
5. `life_records.json`, `life_session_state.json`, 잠금 파일, 사용자 `prompts/life_world.md`와 다른 사용자 런타임 파일은 mapping과 archive에서 제외됐는지 확인한다.
6. Microsoft Store Python smoke에서는 별도의 `store_smoke/<GUID>` 상대 경로만 사용해 Roaming 권위 파일 우선, stale cache 복구, 손상 권위 파일의 fail-closed 동작을 확인한다. 종료 시 검증한 해당 디렉터리만 정리한다.

민감 데이터가 발견되면 새 commit, tag와 release를 중단한다. 이미 Git history나 release asset에 포함됐다면 현재 파일만 지우지 말고 history rewrite와 기존 tag·asset 교체 필요 여부를 먼저 판단한다.

집중 테스트 명령과 수동 확인 목록은 [TESTING.md](../TESTING.md#생활-기록-회귀-테스트)를 참고한다.
